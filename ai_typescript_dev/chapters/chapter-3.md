# Часть 2: Переход к продвинутому TypeScript AI Stack для Salomon

Переходим к проработке тем, которые вы будете непосредственно проектировать и внедрять в кодовую базу Salomon (согласно вашему плану `plan.md` и требованиям вакансии).

## Тема A: Продвинутый RAG & Борьба с "Lost in the Middle" (Главы 7 и 8)

При построении поиска по технологическим картам материалов (например, мембраны *Gore-Tex*, подошвы *Contagrip*) или инструкциям к креплениям *Salomon Shift*, наивный RAG (простой семантический поиск + отправка топ-10 чанков в Claude) быстро ломается.

### Проблема: "Lost in the Middle" (Утеря в середине) [11.4]
Большие языковые модели (даже с длинным контекстным окном, как у Claude) отлично извлекают информацию из самого начала и самого конца переданного текста. Но если нужная деталь (например, точный вес для настройки усилия срабатывания креплений) зажата где-то на 7-й странице из 15 переданных, модель с высокой вероятностью её проигнорирует или галлюцинирует [11.4].

### Решение: Паттерн "Parent-Document Retriever" + Re-ranking [11.2, 11.4]
Мы разделяем репрезентацию документа для **поиска** и для **генерации** [11.2]:
1.  **Для поиска:** Мы нарезаем PDF на очень мелкие, гранулярные чанки (по 100-200 токенов), чтобы векторный поиск (`pgvector`/OpenSearch) мог максимально точно зацепиться за ключевые слова и семантику [11.2].
2.  **Для генерации:** Каждому мелкому чанку мы сопоставляем его «родительский» большой контекст (например, всю главу или страницу целиком) [11.2].
3.  **Реранкинг:** Мы пропускаем первые 20 результатов векторного поиска через Cross-Encoder (например, *Cohere Rerank*), который переупорядочивает их по реальной релевантности запросу, оставляя только топ-3 действительно важных родительских документов для отправки в Claude [11.4].

### Реализация на TypeScript (Vercel AI SDK + Bedrock):

```typescript
// services/rag-retrieval.service.ts
import { bedrock } from '@ai-sdk/amazon-bedrock';
import { generateText } from 'ai';
import { VectorStore } from '../infrastructure/vector-store';
import { Reranker } from '../infrastructure/cohere-reranker';

export class RagRetrievalService {
  constructor(
    private vectorStore: VectorStore,
    private reranker: Reranker
  ) {}

  async answerGearQuery(userQuery: string): Promise<string> {
    // 1. Поиск мелких, точных векторов (Small Chunks)
    const smallChunks = await this.vectorStore.searchSimilar(userQuery, { limit: 20 });

    // 2. Извлечение сопоставленных родительских документов (Parent Documents)
    const parentDocuments = await Promise.all(
      smallChunks.map(chunk => this.vectorStore.getParentDocument(chunk.parentId))
    );

    // Убираем дубликаты родительских документов
    const uniqueParents = [...new Map(parentDocuments.map(doc => [doc.id, doc])).values()];

    // 3. Реранкинг через Cohere для борьбы с "Lost in the Middle"
    const rerankedDocs = await this.reranker.rerank({
      query: userQuery,
      documents: uniqueParents.map(doc => doc.text),
      topN: 3 // Оставляем строго топ-3 наиболее релевантных полных контекстов
    });

    const context = rerankedDocs.map(result => result.text).join('\n\n');

    // 4. Генерация точного ответа через Claude 3.5 Sonnet
    const { text } = await generateText({
      model: bedrock('anthropic.claude-3-5-sonnet-20240620-v1:0'),
      system: `Ты — эксперт Salomon по экипировке. Отвечай на вопросы пользователей, 
               используя только предоставленный проверенный контекст.
               Если в контексте нет ответа, вежливо скажи, что не обладаешь этой информацией.`,
      prompt: `Контекст:\n${context}\n\nВопрос: ${userQuery}`,
    });

    return text;
  }
}
```

## Тема B: Архитектура Агентов и Human-in-the-Loop (Главы 10 и 11)

В Salomon агенты будут решать сложные задачи: например, классификация гарантийных кейсов или подбор кастомной ростовки лыж на основе физических параметров и стиля катания.

### Проблема: Ненадежность и бесконечные циклы
Агенты, работающие в циклах (ReAct — *Reasoning and Acting*), могут зацикливаться: Агент запрашивает инструмент ➔ получает ошибку ➔ запрашивает тот же инструмент с теми же параметрами ➔ уходит в бесконечную петлю, генерируя огромные счета за API-токены.

### Решение: Граф состояний (State Graph) + Human-in-the-Loop [6.3, 9.2]
Вместо линейных цепочек мы строим управляемый конечный автомат:
*   Каждый шаг фиксирует свое состояние в персистентную базу данных (State Persistence) [10.2].
*   Если агент пытается вызвать деструктивный инструмент (например, подтвердить гарантийный возврат денег на карту клиента в CRM), граф приостанавливает выполнение (Interrupt/Gate) и ждет явной аппрув-команды от оператора службы поддержки (Human-in-the-Loop) [6.3].

```
                 [ Начало ]
                     │
                     ▼
             [ Сбор информации ]
                     │
                     ▼
         [ Требуется возврат денег? ]
             ├── Да ──► [ Пауза: Ожидание аппрува менеджера ] ──► [ Проведение транзакции ]
             └── Нет ─► [ Стандартный ответ ]
```

### Паттерн "LLM-as-a-Judge" (ИИ в роли Судьи) [12.1, 15.1]
Мы не можем проверять ответы регулярными выражениями. Мы используем более мощную модель (например, Claude 3.5 Opus или Sonnet с жестким системным промптом) для оценки сгенерированных ответов по трем классическим метрикам [15.2]:
1.  **Faithfulness (Достоверность):** Насколько сгенерированный ответ подтверждается исходным контекстом RAG (отсутствие галлюцинаций) [15.2].
2.  **Answer Relevance (Релевантность):** Насколько ответ решает проблему, озвученную в вопросе [15.2].
3.  **Context Recall (Полнота контекста):** Нашел ли поисковый движок все необходимые детали, которые требуются для ответа [15.2].

### Архитектурный разбор и решение (Ваша выигрышная стратегия на интервью)

#### 1. Устранение зависания RAG (Оптимизация базы данных и запросов)
*   **Проблема:** Медленный векторный поиск по большой таблице embeddings. Скорее всего, в PostgreSQL на колонке вектора не построен или неправильно настроен индекс.
*   **Решение:**
    1.  Нам нужно перевести поиск из режима полного сканирования таблицы (Exact KNN Scan) в режим приблизительного поиска (ANN - Approximate Nearest Neighbor).
    2.  Для этого мы построим **HNSW (Hierarchical Navigable Small World) индекс** в `pgvector` [12.2, 12.3]:
        ```sql
        -- Строим HNSW-индекс по косинусному расстоянию
        CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops);
        ```
    3.  Мы также применим **пайплайнинг с прерыванием (AbortController)**: если запрос к Bedrock или БД висит дольше 5 секунд, мы автоматически отменяем сетевую операцию, чтобы не занимать ресурсы пула соединений Node.js [1.1.2].

#### 2. Защита от опасных рекомендаций (Safety Guardrails)
*   **Проблема:** Модель Claude поддается влиянию промпта пользователя (например, если новичок пишет: *"Я хочу выглядеть круто и купить самые жесткие ботинки"*), игнорируя базовые правила безопасности [11.1, 14.1].
*   **Решение:** Внедрение концепции **Input/Output Guardrail леера** [11.2, 14.2].
    Вместо того чтобы надеяться на одну системную инструкцию Claude, мы оборачиваем вызов модели в двухэтапную валидацию:
    1.  **На входе (Input):** Агент сначала классифицирует уровень катания пользователя с помощью легковесной быстрой модели-классификатора (например, Llama 3 через Bedrock).
    2.  **На выходе (Output Validation via Schema):** Мы заставляем Claude возвращать строго структурированный JSON (с помощью Zod-схемы в Vercel AI SDK). Если модель возвращает жесткость > 100 для уровня "Beginner", наш валидатор на бэкенде автоматически перехватывает этот JSON и перенаправляет запрос на генерацию безопасной альтернативы, либо выдает предупреждение:
        ```typescript
        // Валидация схемы на выходе с помощью Zod
        const bootRecommendationSchema = z.object({
          bootModel: z.string(),
          stiffness: z.number().max(100, { 
            message: "Для новичков жесткость не должна превышать 100" 
          }),
          justification: z.string()
        });
        ```

Этот комплексный ответ покажет, что вы понимаете:
*   Как физически устроена оптимизация баз данных и индексов (HNSW/B-Tree) [12.2].
*   Как писать безопасный, неблокирующий асинхронный код на TypeScript [1.1].
*   Как проектировать надежные и безопасные для бизнеса ИИ-системы на уровне архитектурных паттернов, а не просто "играть с промптами" [2.1].

Чтобы уверенно вести архитектурные дискуссии в команде **AI Enablement в Salomon**, вам важно четко разделять эволюционные этапы развития систем генерации с дополнением извлеченными данными. 

RAG прошел путь от плоских, хрупких скриптов до интеллектуальных, самокорректирующихся агентных систем. Давайте разберем разницу между **Advanced RAG** и **Adaptive RAG (ARAG)** на понятных примерах, коде и физических аналогиях.

---

## 🧭 Иерархия RAG-систем: Сравнительный обзор

```
                             [ 🤖 ADAPTIVE RAG (ARAG) ]
                         Динамический выбор стратегии, 
                         оценка качества в цикле, Query Rewriting.
                                         ▲
                                         │
                             [ 🛠️ ADVANCED RAG ]
                         Фиксированный конвейер:
                         Parent-Doc, Hybrid Search, Re-ranking.
                                         ▲
                                         │
                             [ 🧊 NAIVE RAG ]
                         Простой векторный поиск ➔
                         Вставка в промпт ➔ Генерация.
```

---

### 1. Naive RAG (Простой RAG)
Это база, которую обычно пишут по туториалам: пользователь вводит запрос ➔ мы превращаем его в вектор ➔ ищем топ-3 похожих чанка в базе данных ➔ «впихиваем» их в системный промпт ➔ Claude генерирует ответ.
*   **Где ломается:** База находит нерелевантные чанки (низкая точность), модель путается в куче текста или галлюцинирует, если в найденных документах вообще не было ответа на вопрос.

---

### 2. Advanced RAG (Продвинутый RAG)
Это **фиксированный, но усложненный конвейер** (pipeline). Мы признаем, что поиск работает плохо, и внедряем жесткие инженерные шаги до (*pre-retrieval*) и после (*post-retrieval*) обращения к базе данных:
*   **Pre-retrieval (До поиска):** Семантическое чанкование (деление текста по смысловым абзацам, а не по фиксированному лимиту символов), обогащение чанков метаданными [11.1].
*   **Retrieval (Поиск):** Гибридный поиск (объединение плотных векторов pgvector и разреженного поиска ключевых слов BM25) [11.2, 12.2].
*   **Post-retrieval (После поиска):** **Parent-Document Retrieval** (поиск по мелким чанкам, но отправка в модель крупных родительских разделов) [11.2] и **Re-ranking** (прогон через модель-реранкер, чтобы отсортировать результаты и поднять самое важное наверх, решив проблему *Lost in the Middle*) [11.4].

> **Резюме:** Advanced RAG работает по строгой, неизменяемой цепочке шагов. Он гораздо точнее, но выполняет одну и ту же тяжелую работу и для простого вопроса («Какая гарантия на обувь?»), и для сложного аналитического запроса.

---

### 3. Adaptive RAG (ARAG) — Адаптивный (Агентный) RAG
Это переход от жесткого конвейера к **агентному принятию решений**. Система ведет себя как умный динамический контроллер:
1.  **Query Classification (Классификация):** Сначала быстрая модель анализирует запрос. 
    *   Если вопрос простой и общеизвестный («Привет! Кто ты?»), RAG вообще не запускается (экономим ресурсы и время).
    *   Если вопрос требует актуальных внешних данных («Какая жесткость у ботинок Salomon Shift 2026 года?»), запрос направляется в векторную базу данных.
2.  **Self-Correction Loop (Самокоррекция в цикле):** Агент извлекает документы, но перед тем как отдать их пользователю, он запускает **внутренний аудит (Self-Grading)**:
    *   *Шаг А:* Достаточно ли этой информации для ответа? Если нет, агент переписывает запрос другими словами (**Query Rewriting**) и делает повторный поиск.
    *   *Шаг Б:* Соответствует ли сгенерированный ответ фактам из документов? (Проверка на галлюцинации).

---

## 🏔️ Ментальная модель: Проводник на вершину Монблан

*   **Naive RAG:** Карта маршрута на клочке бумаги. Вы идете строго по ней. Если на пути обвал или пошел ливень, вы теряетесь или падаете в расщелину.
*   **Advanced RAG:** Отличная топографическая карта, альтиметр, прогноз погоды перед выходом и качественное снаряжение. Маршрут все еще жестко зафиксирован, но вы подготовлены намного лучше.
*   **Adaptive RAG (ARAG):** **Живой профессиональный гид-альпинист**. Он оценивает ваше состояние на каждом шаге. Если тропа заблокирована, он меняет маршрут на ходу (Query Rewrite). Если погода идеальная и вы в отличной форме, он ведет вас быстрой короткой тропой (No retrieval/Bypass). Если ситуация критическая, он принимает решение развернуться назад (Fallback).

## 🛠️ Реализация Adaptive RAG на TypeScript (Vercel AI SDK + Bedrock)

В Salomon вы будете разрабатывать подобные компоненты для общего SDK. Ниже представлена реализация **Adaptive RAG** конвейера с классификацией запроса и проверкой релевантности документов (Self-Grading loop):

```typescript
// services/adaptive-rag.service.ts
import { generateText, generateObject } from 'ai';
import { bedrock } from '@ai-sdk/amazon-bedrock';
import { z } from 'zod';
import { VectorStore } from '../infrastructure/vector-store';

export class AdaptiveRagService {
  constructor(private vectorStore: VectorStore) {}

  async handleQuery(userQuery: string): Promise<string> {
    const model = bedrock('anthropic.claude-3-5-sonnet-20240620-v1:0');

    // ШАГ 1: Классификация сложности и интента запроса (Query Classifier)
    const { object: classification } = await generateObject({
      model,
      schema: z.object({
        complexity: z.enum(['SIMPLE', 'COMPLEX', 'OUT_OF_SCOPE']),
        rewrittenQuery: z.string().describe('Оптимизированный поисковый запрос для векторной базы данных')
      }),
      system: `Проанализируй запрос пользователя к базе знаний Salomon. 
               Определи, требует ли он обращения к технической документации (COMPLEX) 
               или это простой вопрос/приветствие (SIMPLE).`,
      prompt: userQuery,
    });

    // Маршрутизация на основе классификации (Dynamic Routing)
    if (classification.complexity === 'SIMPLE') {
      return this.generateDirectAnswer(userQuery);
    }

    if (classification.complexity === 'OUT_OF_SCOPE') {
      return "Извините, я могу помочь вам только с вопросами об экипировке Salomon.";
    }

    // ШАГ 2: Адаптивный цикл поиска с самокоррекцией (Self-Correction Loop)
    let attempts = 0;
    let context = '';
    let searchQuery = classification.rewrittenQuery;

    while (attempts < 2) {
      // Выполняем поиск по оптимизированному запросу
      const retrievedDocs = await this.vectorStore.search(searchQuery, { limit: 3 });
      context = retrievedDocs.map(d => d.text).join('\n\n');

      // Шаг оценки: Достаточно ли документов для ответа? (Document Relevance Grader)
      const { object: grading } = await generateObject({
        model,
        schema: z.object({
          isRelevant: z.boolean().describe('Содержит ли контекст достаточно фактов для точного ответа на вопрос'),
          newSearchQuery: z.string().optional().describe('Если нерелевантно, перепиши поисковый запрос по-другому')
        }),
        system: `Ты — аудитор качества RAG. Сверь контекст и вопрос. 
                 Определи, есть ли в контексте фактический ответ на этот вопрос.`,
        prompt: `Вопрос: ${userQuery}\n\nКонтекст:\n${context}`
      });

      if (grading.isRelevant) {
        break; // Документы релевантны, выходим из цикла поиска
      }

      // Если документы нерелевантны — переписываем запрос и пробуем еще раз (Query Reformulation)
      searchQuery = grading.newSearchQuery || searchQuery;
      attempts++;
    }

    // ШАГ 3: Финальная генерация ответа на основе проверенного контекста
    const { text: finalAnswer } = await generateText({
      model,
      system: `Используй предоставленный контекст для точного ответа на вопрос. 
               Если контекст пуст или в нем нет ответа, скажи, что информация не найдена.`,
      prompt: `Контекст:\n${context}\n\nВопрос: ${userQuery}`
    });

    return finalAnswer;
  }

  private async generateDirectAnswer(prompt: string): Promise<string> {
    const { text } = await generateText({
      model: bedrock('anthropic.claude-3-5-sonnet-20240620-v1:0'),
      prompt
    });
    return text;
  }
}
```

### В чем ценность этой архитектуры для Salomon?
1.  **Оптимизация затрат (Cost Efficiency):** Мы не тратим ресурсы на векторный поиск по простым запросам.
2.  **Защита от галлюцинаций (Hallucination Prevention):** Если первый поиск вернул "мусор", система не будет генерировать ответ на его основе. Она перепишет запрос и попробует найти факты заново.
3.  **Гибкость:** Этот сервис легко оборачивается в абстрактный класс `BaseAgent`, позволяя другим продуктовым командам Salomon использовать умный RAG "из коробки" для своих локальных задач поддержки [chapter-2.md].

### Является ли Adaptive RAG (ARAG) лучшим решением?

**Нет, в архитектуре ИИ нет понятия «абсолютно лучший паттерн» (серебряной пули).** ARAG — это наиболее мощное и интеллектуальное решение для сложных, непредсказуемых задач, но за его гибкость приходится платить конкретную цену [2.1]. 

При выборе архитектуры RAG-пайплайна для конкретного кейса в Salomon вам нужно будет оценивать инженерные компромиссы по следующей матрице:

| Критерий | Naive RAG | Advanced RAG (Static) | Adaptive RAG (Agentic) |
| :--- | :--- | :--- | :--- |
| **Точность (Accuracy)** | Низкая (высокий риск галлюцинаций) | Высокая (для предсказуемых документов) | **Максимальная** (за счет самокоррекции и переписывания запросов) |
| **Задержка (Latency)** | **Минимальная** (~1–2 сек) | Средняя (~2–4 сек, зависит от реранкера) | Высокая (~4–10 сек из-за множественных вызовов LLM на классификацию и оценку) |
| **Стоимость (Cost)** | **Минимальная** (1 запрос к LLM) | Средняя (1 запрос + затраты на API реранкера) | Высокая (несколько последовательных вызовов LLM в цикле) [9.3] |
| **Сложность отладки** | Легко (линейный код) | Средняя | **Очень высокая** (нелинейный граф состояний, сложно логировать) [9.1] |

#### Когда что выбирать в Salomon:
*   **Naive RAG:** Для внутренних черновых прототипов или очень простых, хорошо структурированных FAQ.
*   **Advanced RAG:** Для стандартного поиска по фиксированным базам знаний (например, инструкции к креплениям или таблицы размеров) [11.2, 11.4]. Здесь задержка должна быть минимальной, а структура документов предсказуема.
*   **Adaptive RAG (ARAG):** Для интеллектуальных агентов поддержки клиентов, которые обрабатывают свободную речь [14.1]. Пользователь может спросить: *«Привет! Посоветуй мне лыжи, а еще расскажи, как работает ваша доставка в Польшу и можно ли вернуть товар, если он не подошел?»* [plan.md] (Здесь нужны динамическая маршрутизация, переписывание запросов и оценка релевантности документов на ходу).

## 1. Проектирование RAG-пайплайнов (RAG Pipeline Design)

Вы должны свободно владеть терминологией продвинутого извлечения данных:

### Стратегии нарезки текста (Chunking):
*   *Наивный подход:* Нарезка по фиксированному числу символов (например, каждые 500 символов) — ломает контекст посередине предложения.
*   *Семантический подход (Semantic Chunking):* Нарезка на основе плотности изменения векторов предложений. Мы делим текст там, где резко меняется тема обсуждения [11.1].
*   *Макетный подход (Layout-aware):* Парсинг PDF с учетом структуры (заголовки h1-h3, списки, выделение таблиц в формат Markdown). Для Salomon это критично, так как спецификации экипировки часто хранятся в виде таблиц в PDF.

### Гибридный поиск (Hybrid Search):
*   Вы должны объяснить, почему векторного поиска (Dense Retrieval) недостаточно. Векторный поиск отлично понимает синонимы («обувь для бега по грязи» ➔ *Speedcross 6*), но полностью слеп к точным артикулам или серийным номерам.
*   **Решение:** Объединение векторного поиска по косинусному сходству и классического текстового поиска **BM25 (Sparse Retrieval)** через алгоритм взаимного ранжирования **RRF (Reciprocal Rank Fusion)** [11.2, 12.1, 12.2].

## 2. Архитектура Агентов (Agentic Patterns)

Интервьюеры будут проверять, умеете ли вы строить надежных агентов:

*   **Управление контекстным окном (Context Window Management):**
    *   При долгом диалоге контекстное окно Claude забивается старыми сообщениями, что замедляет ответы и увеличивает стоимость [12.3].

# Часть 1: Как отвечать на вопрос «Как спроектировать Salomon AI SDK?»

Вам нужно показать системный, архитектурный подход. Опишите дизайн SDK через **5 фундаментальных слоев (Pillars)**:

```
                      [ @salomon/ai-sdk ]
 ┌────────────────────────────────────────────────────────┐
 │ 1. Core Abstractions (ITextGenerator, IChatModel)      │
 ├────────────────────────────────────────────────────────┤
 │ 2. Provider Adapters (AWS Bedrock, Anthropic API)      │
 ├────────────────────────────────────────────────────────┤
 │ 3. Resiliency Layer (Retries, Circuit Breaker, Limits) │
 ├────────────────────────────────────────────────────────┤
 │ 4. Observability Layer (OpenTelemetry / OpenLLMetry)   │
 ├────────────────────────────────────────────────────────┤
 │ 5. Prompt Management (XML Schema, Prompt Caching)      │
 └────────────────────────────────────────────────────────┘
```

### 1. Framework Agnostic Core (Независимость от фреймворков)
*   **Архитектура:** Ядро SDK должно быть написано на чистом TypeScript/Node.js без привязки к конкретному веб-фреймворку (будь то NestJS, Express или Next.js). 
*   **Реализация:** Мы упаковываем SDK как приватный scoped-пакет `@salomon/ai-sdk` в AWS CodeArtifact. Для команд, пишущих на NestJS, мы предоставляем легкий модуль-адаптер (`SalomonAiModule`), который регистрирует провайдеры в DI-контейнере [2.3].

### 2. Строгая типизация и схемы валидации (Zod)
*   **Архитектура:** SDK должен заставлять команды возвращать строго типизированные ответы от Claude (Structured Outputs) [2.1].
*   **Реализация:** Мы интегрируем валидацию схем через Zod непосредственно в интерфейс вызова SDK. Если модель возвращает некорректный JSON, SDK под капотом перехватывает ошибку, автоматически отправляет повторный запрос (Self-Correction Prompt) с указанием ошибки парсинга и возвращает валидный типизированный объект [2.1].

### 3. Слой устойчивости и безопасности (Resiliency & Guardrails)
*   **Архитектура:** SDK должен защищать внешние лимиты API и пул соединений Node.js [1.1.2].
*   **Реализация:** Мы встраиваем в SDK:
    *   **Лимиты и очереди:** Использование очередей с ограничением частоты запросов (Rate Limiting) на основе `p-limit` или `p-retry` для предотвращения ошибок HTTP 429 от AWS Bedrock [1.1.2].
    *   **Предохранитель (Circuit Breaker):** Если AWS Bedrock в регионе `eu-central-1` выдает ошибки 5xx несколько раз подряд, предохранитель разрывает цепь и автоматически переключает запросы на резервный регион или прямой Anthropic API (паттерн *Fallback*) [2.2, 2.3].

### 4. Сквозная наблюдаемость (Observability)
*   **Архитектура:** Команды не должны вручную настраивать логирование каждого шага ИИ [15.3].
*   **Реализация:** SDK «из коробки» поддерживает стандарт **OpenTelemetry (OpenLLMetry)**. Каждый вызов автоматически генерирует спаны (Spans) с метаданными: количество отправленных/полученных токенов, задержка (latency), имя модели и ID пользователя [15.3]. Эти данные бесшовно улетают в Datadog, Dynatrace или Prometheus [15.3].

### 5. Менеджмент промптов и кэширование
*   **Архитектура:** Промпты не должны быть захардкожены в виде строк внутри бизнес-кода продуктовых команд [plan.md].
*   **Реализация:** SDK предоставляет шаблонизатор промптов, поддерживающий XML-структурирование (рекомендация Anthropic для Claude) [plan.md]. Он автоматически настраивает **Prompt Caching** в AWS Bedrock для тяжелых системных промптов (что снижает стоимость входящих токенов до 85% и снижает latency при частых запросах) [plan.md].

## 2. Разделяемые объединения (Discriminated Unions) для состояний Агента

В агентных системах и графах состояний (например, при написании аналогов LangGraph на TypeScript) критически важно не допускать «невозможных» состояний системы [9.2].

### Вопрос: «Как вы спроектируете тип для State Graph агента, чтобы исключить баги типизации?»
*   **Что отвечать:** Мы используем паттерн **Discriminated Unions** (размеченные объединения). Мы создаем общий литеральный тип-дискриминатор (например, `status`), по которому TypeScript на этапе компиляции будет строго определять, какие поля доступны в объекте, а какие нет.
*   **Пример кода:**
    ```typescript
    // Шаг 1: Описываем все возможные состояния агента
    type AgentIdleState = {
      status: 'idle';
    };

    type AgentRunningState = {
      status: 'running';
      activeTool: string;   // Поле доступно только при статусе running
      startTime: number;
    };

    type AgentPausedState = {
      status: 'paused_for_approval';
      pendingTransactionId: string; // Поле доступно только при паузе
    };

    // Шаг 2: Создаем объединенный тип состояния
    export type AgentState = AgentIdleState | AgentRunningState | AgentPausedState;

    export function handleAgentState(state: AgentState) {
      if (state.status === 'running') {
        // TypeScript ОЧЕНЬ строго знает, что здесь доступны state.activeTool и state.startTime,
        // но попытка обратиться к state.pendingTransactionId вызовет ошибку компиляции!
        console.log(`Executing tool: ${state.activeTool}`);
      }
    }
    ```

### Вопрос: «Как написать обобщенную (Generic) функцию для получения строго типизированного JSON от Claude?»
*   **Что отвечать:** Мы пишем обобщенную функцию, которая принимает Zod-схему как аргумент. Zod автоматически выводит статический тип TypeScript с помощью утилиты `z.infer<T>`, гарантируя полную типобезопасность на обоих уровнях [2.1].

    ```typescript

    import { bedrock } from '@ai-sdk/amazon-bedrock';

    // Функция принимает дженерик T, который наследуется от ZodSchema
    export async function fetchStructuredOutput<T extends ZodSchema>(
      prompt: string,
      schema: T
    ): Promise<z.infer<T>> { // Возвращает тип, выведенный из схемы!
      
      const { object } = await generateObject({
        model: bedrock('anthropic.claude-3-5-sonnet-20240620-v1:0'),
        schema,
        prompt,
      });

      return object; // Гарантированно возвращает объект правильного типа в рантайме
    }

    // Использование в коде Salomon:
    const recommendationSchema = z.object({
      bootModel: z.string(),
      stiffness: z.number()
    });

    // TypeScript автоматически выведет тип: { bootModel: string, stiffness: number }
    const result = await fetchStructuredOutput("Посоветуй ботинки...", recommendationSchema);
    ```

## 4. Пользовательские сужения типов (Custom Type Guards)

В AI-пайплайнах данные часто приходят в формате `unknown` или `any` (например, при чтении истории из внешней БД) [10.2].

*   **Пример кода:**
    ```typescript

      toolName: string;
      args: Record<string, any>;
    }

    // Функция-валидатор возвращает предикат типа
    export function isToolCall(input: any): input is ToolCall {
      return (
        input !== null &&
        typeof input === 'object' &&
        typeof input.toolName === 'string' &&
        typeof input.args === 'object'
      );
    }

    export function execute(payload: unknown) {
      if (isToolCall(payload)) {
        // Внутри этого блока payload автоматически сужается до типа ToolCall
        console.log(`Running: ${payload.toolName}`);
      }
    }
    ```

### Вопрос: «Локальная токенизация текста перед отправкой в Claude нагружает CPU. Как сделать так, чтобы тяжелый расчет не заблокировал Event Loop для других пользователей?» [1.1.4]

# you asked

что это function* почему звездочка ?

---

# googleaistudio response

Синтаксис **`function*`** (функция со звездочкой) в JavaScript и TypeScript объявляет особую категорию функций — **Генераторы (Generator Functions)**.

Звездочка после слова `function` сообщает движку JavaScript (например, V8 в Node.js), что эта функция будет вести себя не так, как обычная. 

---

### 🧠 Ментальная модель: Автомат с газировкой

*   **Обычная функция (`function`)** — это как повар, который вываливает перед вами на стол сразу 1000 блинов. Вам приходится освобождать много места (тратить оперативную память), даже если вы съедите всего два блина. Обычная функция всегда выполняется от первой строчки до слова `return` без остановок.
*   **Функция-генератор (`function*`)** — это умный **автомат с едой**. Когда вы «вызываете» его, он не выдает вам все продукты сразу. Он просто включается и ждет. Каждый раз, когда вы нажимаете кнопку (вызываете метод `.next()`), автомат выдает вам строго один предмет (через ключевое слово **`yield`**) и снова засыпает (ставит выполнение кода на паузу), запоминая свое состояние.

---

### Как это выглядит в коде?

Давайте посмотрим на простейший синхронный генератор:

```typescript
// Звездочка указывает, что это генератор
function* numberGenerator() {
  console.log("Старт генератора");
  yield 1; // Код остановится прямо здесь после выдачи единицы!
  
  console.log("Продолжаем работу");
  yield 2; // Код остановится здесь
  
  console.log("Конец работы");
  return 3;
}

// 1. Вызов функции НЕ запускает код внутри неё! Он просто создает объект-генератор.
const gen = numberGenerator(); 

// 2. Делаем первый шаг
console.log(gen.next()); 
// Выведет: "Старт генератора"
// И вернет объект: { value: 1, done: false }

// 3. Делаем второй шаг
console.log(gen.next()); 
// Выведет: "Продолжаем работу"
// И вернет объект: { value: 2, done: false }

// 4. Делаем финальный шаг
console.log(gen.next()); 
// Выведет: "Конец работы"
// И вернет объект: { value: 3, done: true } (done: true означает, что генератор завершен)
```

### Зачем это нужно в AI-разработке и при работе с Claude?

В Salomon вы будете использовать **асинхронные генераторы (`async function*`)** [1.1.3]. Это фундамент для **стриминга токенов** [1.1.3].

Когда Claude генерирует ответ на 1000 слов, генерация занимает около 10 секунд. Мы не хотим заставлять пользователя смотреть на пустой экран 10 секунд. Мы хотим отдавать слова по мере их генерации [1.1.3]. 

С помощью `async function*` мы можем написать красивый, неблокирующий стриминговый шлюз:

```typescript
import { BedrockRuntimeClient, InvokeModelWithResponseStreamCommand } from '@aws-sdk/client-bedrock-runtime';

const client = new BedrockRuntimeClient({ region: 'eu-central-1' });

// Асинхронный генератор: возвращает токены по одному по мере их прихода из сети
export async function* streamClaudeTokens(prompt: string): AsyncGenerator<string, void, unknown> {
  const command = new InvokeModelWithResponseStreamCommand({
    modelId: 'anthropic.claude-3-5-sonnet-20240620-v1:0',
    contentType: 'application/json',
    accept: 'application/json',
    body: JSON.stringify({
      anthropic_version: 'bedrock-2023-05-31',
      max_tokens: 1000,
      messages: [{ role: 'user', content: prompt }]
    })
  });

  const response = await client.send(command);

  if (response.body) {
    // Читаем сетевой поток чанков от AWS Bedrock
    for await (const event of response.body) {
      if (event.chunk) {
        const chunkJson = JSON.parse(new TextDecoder().decode(event.chunk.bytes));
        
        // Извлекаем только что сгенерированное слово (токен)
        if (chunkJson.type === 'content_block_delta') {
          const token = chunkJson.delta.text;
          
          // Отдаем токен клиенту и ставим функцию на паузу, ожидая следующий чанк из сети
          yield token; 
        }
      }
    }
  }
}
```

### Как этот поток потребляется на сервере (например, в Express/NestJS):

```typescript
app.get('/api/recommend', async (req, res) => {
  // Настраиваем Server-Sent Events (SSE) для стриминга в браузер
  res.setHeader('Content-Type', 'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache');

  const tokenStream = streamClaudeTokens("Посоветуй ботинки для фрирайда...");

  // Мы итерируемся по асинхронному генератору с помощью цикла "for await...of"
  for await (const token of tokenStream) {
    res.write(`data: ${JSON.stringify({ text: token })}\n\n`); // Мгновенно отправляем токен пользователю
  }

  res.end(); // Закрываем соединение, когда генератор завершил работу
});
```

### Резюме для интервью:
Звездочка превращает обычную функцию в **функцию-паузу (генератор)**. В AI-инженерии это стандарт де-факто для эффективного и неблокирующего стриминга данных от LLM, который позволяет снизить время ожидания ответа пользователем до абсолютного минимума [1.1.3].
