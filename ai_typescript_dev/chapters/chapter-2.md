# Глава 2: Лыжные крепления-трансформеры — Паттерны SOLID и чистая архитектура в AI

Представьте себе профессионального лыжника, который готовится к заезду во фрирайде. Ночью прошел сильный снегопад, поэтому ему нужны широкие лыжи для глубокого пухляка. На следующий день трассу подморозило, и для лучшей управляемости требуются жесткие трассовые лыжи. 

Вместо того чтобы покупать три пары лыж со встроенными намертво ботинками, он использует **универсальную платформу креплений**. Ботинки жестко фиксируются в креплении, а само крепление устанавливается на любую пару лыж по стандартным пазам. Ботинок (ваша бизнес-логика) не знает деталей скользящей поверхности лыжи (конкретная модель ИИ). Он просто полагается на стандартизированный замок крепления (интерфейс) [2.1].

Когда разработчики создают AI-приложения, они часто совершают критическую ошибку: намертво «припаивают» официальный SDK (например, `@aws-sdk/client-bedrock-runtime` или `@anthropic-ai/sdk`) прямо в код контроллеров и сервисов. В результате, когда провайдер меняет формат запросов или компания решает сэкономить, перейдя на другую модель, приходится переписывать и тестировать заново всё приложение.

В этой главе мы применим классические принципы проектирования **SOLID** и паттерны **Чистой Архитектуры**, чтобы сделать наши интеграции с моделями такими же гибкими, как спортивные крепления-трансформеры.

## 📐 1. Принципы SOLID в мире недетерминированного AI

Традиционное программное обеспечение детерминировано: на вход `2 + 2` мы всегда получаем `4`. Модели искусственного интеллекта ведут себя иначе — они вероятностны. Один и тот же запрос может вернуть разные формулировки. Чтобы управлять этим хаосом, архитектура вокруг модели должна быть максимально строгой и предсказуемой [2.1].

```
❌ Плохой подход (Спагетти-код):
[Контроллер] ──► Строит промпт ──► Вызывает Bedrock SDK ──► Парсит JSON ──► Пишет в DB

⚡ Чистый подход (SOLID):
[Контроллер] ──► [PromptBuilder]
             ──► [LLMProvider (Интерфейс)] ◄── [ClaudeBedrockAdapter]
             ──► [ResponseParser]
             ──► [UserRepository]
```

### S: Single Responsibility Principle (Принцип единственной ответственности)
Класс или функция должны иметь только одну причину для изменения. 
*   *Нарушение:* Сервис, который одновременно конструирует текст промпта, делает сетевой запрос в AWS Bedrock, обрабатывает ошибки таймаута, парсит Markdown-вывод модели в JSON и записывает результат в базу данных. Если Salomon поменяет структуру базы данных или Anthropic обновит Claude — этот гигантский класс придется переписывать.
*   *Решение:* Разделите процесс на специализированные компоненты: `PromptBuilder` отвечает только за сборку текста, `LLMAdapter` — за транспорт и сеть, `ResponseParser` — за валидацию схемы вывода, а `DBRepository` — за персистентность.

### O: Open/Closed Principle (Принцип открытости/закрытости)
Компоненты должны быть открыты для расширения, но закрыты для модификации [2.2].
*   *Решение:* Ваша бизнес-логика (например, рекомендатель товаров) должна зависеть от абстрактного интерфейса `LLMProvider`. Если вам нужно добавить модель Llama от Meta, вы не меняете код рекомендателя. Вы просто пишете новый класс `LlamaAdapter`, который реализует тот же интерфейс [2.2].

### L: Liskov Substitution Principle (Принцип подстановки Лисков)
Объекты в программе должны быть заменяемыми на экземпляры их подтипов без изменения правильности работы программы.
*   *Решение:* Любой адаптер модели (`ClaudeBedrockAdapter`, `OpenAIAdapter`, `MockLLMAdapter` для тестов) должен вести себя предсказуемо. Если один адаптер возвращает структурированный объект при успехе, другие не должны возвращать сырую строку или падать с неожиданными ошибками. Они должны строго следовать контракту интерфейса.

### I: Interface Segregation Principle (Принцип разделения интерфейса)
Клиенты не должны зависеть от методов, которые они не используют.
*   *Решение:* Не создавайте один гигантский интерфейс `IGiantModelInterface`, содержащий методы для генерации текста, создания эмбеддингов, распознавания речи и генерации картинок. Разделите его на тонкие интерфейсы: `ITextGenerator`, `IEmbeddingGenerator`, `IImageGenerator`.

### D: Dependency Inversion Principle (Принцип инверсии зависимостей)
Модули верхних уровней не должны зависеть от модулей нижних уровней. Оба должны зависеть от абстракций [2.3].
*   *Решение:* Наш высокоуровневый сервис оформления возвратов не должен импортировать конкретный класс `AWSBedrockClient`. Вместо этого мы внедряем зависимость в виде интерфейса `LLMProvider` [2.3].

## 🧱 2. Паттерны "Адаптер" и "Репозиторий" в действии

Давайте перенесем теорию в код на TypeScript. Мы спроектируем систему, которая позволяет вызывать разные модели через единый интерфейс.

### Шаг 1: Определяем абстрактный контракт (Интерфейс)

```typescript
// types/llm.ts

export interface LLMRequestOptions {
  temperature?: number;
  maxTokens?: number;
}

export interface LLMResponse {
  text: string;
  usage: {
    promptTokens: number;
    completionTokens: number;
  };
}

// Тонкий интерфейс для генерации текста
export interface ITextGenerator {
  generate(prompt: string, options?: LLMRequestOptions): Promise<LLMResponse>;
}
```

### Шаг 2: Создаем конкретный Адаптер для AWS Bedrock (Claude)

```typescript
// adapters/claude-bedrock.adapter.ts
import { ITextGenerator, LLMRequestOptions, LLMResponse } from '../types/llm';
import { BedrockRuntimeClient, InvokeModelCommand } from '@aws-sdk/client-bedrock-runtime';

export class ClaudeBedrockAdapter implements ITextGenerator {
  private client: BedrockRuntimeClient;
  private modelId = 'anthropic.claude-3-5-sonnet-20240620-v1:0';

  constructor(region: string = 'eu-central-1') {
    this.client = new BedrockRuntimeClient({ region });
  }

  async generate(prompt: string, options?: LLMRequestOptions): Promise<LLMResponse> {
    const payload = {
      anthropic_version: 'bedrock-2023-05-31',
      max_tokens: options?.maxTokens ?? 1000,
      temperature: options?.temperature ?? 0.3,
      messages: [{ role: 'user', content: prompt }],
    };

    try {
      const command = new InvokeModelCommand({
        modelId: this.modelId,
        contentType: 'application/json',
        accept: 'application/json',
        body: JSON.stringify(payload),
      });

      const response = await this.client.send(command);
      const responseBody = JSON.parse(new TextDecoder().decode(response.body));

      return {
        text: responseBody.content[0].text,
        usage: {
          promptTokens: responseBody.usage?.input_tokens ?? 0,
          completionTokens: responseBody.usage?.output_tokens ?? 0,
        },
      };
    } catch (error) {
      throw new Error(`Ошибка AWS Bedrock при вызове Claude: ${(error as Error).message}`);
    }
  }
}
```

## 💉 3. Продвинутое внедрение зависимостей и горячая замена

Теперь свяжем компоненты с помощью концепции **внедрения зависимостей (Dependency Injection)** [2.3]. Покажем, как это выглядит в архитектурном стиле NestJS, который широко используется для построения корпоративных систем на Node.js.

```typescript
// app.module.ts
import { Module } from '@nestjs/common';
import { RecommendationController } from './recommendation.controller';
import { RecommendationService } from './recommendation.service';
import { ClaudeBedrockAdapter } from './adapters/claude-bedrock.adapter';

@Module({
  controllers: [RecommendationController],
  providers: [
    RecommendationService,
    {
      // Регистрируем наш интерфейс как токен для DI-контейнера
      provide: 'ITextGenerator',
      // В зависимости от конфигурации окружения (env) мы можем легко подставить другой класс
      useFactory: () => {
        if (process.env.AI_PROVIDER === 'mock') {
          return new MockLLMAdapter(); // Для локальных тестов без интернета
        }
        return new ClaudeBedrockAdapter(process.env.AWS_REGION || 'eu-central-1');
      },
    },
  ],
})
export class AppModule {}
```

Использование в сервисе:

```typescript
// recommendation.service.ts
import { Injectable, Inject } from '@nestjs/common';
import { ITextGenerator } from './types/llm';

@Injectable()
export class RecommendationService {
  // Внедряем интерфейс, а не конкретный класс. Сервис ничего не знает про AWS Bedrock!
  constructor(
    @Inject('ITextGenerator') private readonly llm: ITextGenerator
  ) {}

  async getGearGuide(userSkill: string): Promise<string> {
    const prompt = `Порекомендуй лыжи Salomon для уровня катания: "${userSkill}".`;
    
    const response = await this.llm.generate(prompt);
    return response.text;
  }
}
```

## 🧪 4. Тестирование недетерминированных систем

Написание юнит-тестов для AI-функций часто пугает разработчиков: *«Как я могу проверить результат работы теста, если Claude каждый раз возвращает немного разный текст?»*

Чистая архитектура делает эту задачу тривиальной. Мы разделяем тесты на две категории:
1.  **Юнит-тесты бизнес-логики (Детерминированные):** Мы полностью исключаем настоящие запросы в сеть и заменяем наш `ITextGenerator` на предсказуемый `MockLLMAdapter` [2.4].
2.  **Интеграционные тесты (Инфраструктурные):** Мы тестируем только сам `ClaudeBedrockAdapter`, проверяя корректность сетевых запросов и сериализацию данных.

### Шаг 1: Создаем Mock-адаптер для тестов

```typescript
// mocks/llm.mock.ts
import { ITextGenerator, LLMResponse } from '../types/llm';

export class MockLLMAdapter implements ITextGenerator {
  public lastPrompt: string = '';
  public mockResponse: string = 'Рекомендация: Salomon S/Max 10';

  async generate(prompt: string): Promise<LLMResponse> {
    this.lastPrompt = prompt; // Фиксируем, что пришло на вход
    return {
      text: this.mockResponse,
      usage: { promptTokens: 10, completionTokens: 5 },
    };
  }
}
```

### Шаг 2: Пишем чистый юнит-тест сервиса

```typescript
// recommendation.service.spec.ts
import { RecommendationService } from './recommendation.service';
import { MockLLMAdapter } from './mocks/llm.mock';

describe('RecommendationService', () => {
  it('должен корректно формировать промпт и возвращать рекомендацию', async () => {
    // 1. Создаем заглушку
    const mockLlm = new MockLLMAdapter();
    mockLlm.mockResponse = 'Тестовые лыжи: Salomon QST 98';

    // 2. Внедряем ее вручную в тестируемый сервис (без старта всего NestJS)
    const service = new RecommendationService(mockLlm);

    // 3. Выполняем метод
    const result = await service.getGearGuide('Эксперт фрирайда');

    // 4. Проверяем утверждения (Assertions)
    expect(result).toContain('Salomon QST 98');
    expect(mockLlm.lastPrompt).toContain('Эксперт фрирайда'); // Проверяем, что промпт собран правильно!
  });
});
```

Этот тест выполнится за 2 миллисекунды, не потребует подключения к интернету и не потратит ни одного цента из бюджета Salomon на AWS API [2.4].

## 💬 Симулятор сложного интервью (The Quirky Interview)

### Сценарий
> *«Anthropic выпустила новую версию модели Claude с полностью измененной схемой JSON-ответов. Одновременно с этим в регионе AWS eu-central-1 произошел глобальный сбой, из-за чего доступ к Bedrock пропал. Расскажите, как спроектированная вами архитектура позволит переключить ИИ-ассистента Salomon на резервного провайдера (например, прямой API OpenAI) менее чем за 10 секунд без пересборки Docker-образов и без остановки серверов?»* [2.2]

---

### Архитектурный разбор и решение

#### 1. Стратегия горячего переключения (Hot-swapping)
Для решения этой задачи в реальном времени мы должны использовать комбинацию трех подходов:
*   **Абстракция интерфейсов:** Наша бизнес-логика зависит только от интерфейса `ITextGenerator`, поэтому ей безразлично, кто именно выполняет работу под капотом [2.3].
*   **Динамическая фабрика в DI-контейнере:** Наш провайдер в NestJS инициализирует нужный адаптер динамически, опираясь на внешние переменные конфигурации (Environment Variables) [2.3].
*   **Внешний конфигуратор (Feature Flags или Config Store):** Чтобы не перезапускать сервера для смены переменных окружения, мы используем легкую базу данных конфигураций (например, Redis или AWS AppConfig), которую наше приложение опрашивает раз в несколько секунд (или получает push-уведомления).

#### 2. Реализация динамического переключателя

Мы модифицируем регистрацию нашего провайдера, сделав его чувствительным к динамическому изменению флага в Redis:

```typescript
// providers/dynamic-llm.provider.ts
import { ClaudeBedrockAdapter } from '../adapters/claude-bedrock.adapter';
import { OpenAIAdapter } from '../adapters/openai.adapter';
import { RedisConfigService } from '../services/redis-config.service';

export const DynamicLLMProvider = {
  provide: 'ITextGenerator',
  useFactory: async (configService: RedisConfigService) => {
    // Каждые несколько секунд приложение сверяет активного провайдера в памяти
    return {
      async generate(prompt: string, options?: any) {
        // Читаем активного провайдера из быстрого кэша Redis
        const activeProvider = await configService.get('ACTIVE_AI_PROVIDER');

        if (activeProvider === 'openai') {
          return new OpenAIAdapter().generate(prompt, options);
        }
        
        // По умолчанию используем AWS Bedrock (Claude)
        return new ClaudeBedrockAdapter().generate(prompt, options);
      }
    };
  },
  inject: [RedisConfigService],
};
```

#### 3. Действия во время инцидента
Когда происходит авария:
1. Инженер дежурной смены Salomon заходит в панель управления (или запускает скрипт) и меняет значение в Redis: `SET ACTIVE_AI_PROVIDER "openai"`.
2. При следующем запросе пользователя система считывает новое значение и мгновенно перенаправляет поток генерации на API OpenAI.
3. **Результат:** Инцидент исчерпан за 3 секунды. Ни один Docker-контейнер не перезапускался, бизнес-логика оформления возвратов или подбора экипировки не изменилась ни на символ [2.2].

# 📖 Глоссарий терминов (Главы 1 и 2)

### A
*   **AWS Bedrock** — полностью управляемый облачный сервис от Amazon Web Services, предоставляющий единый безопасный API для доступа к базовым ИИ-моделям (Claude, Llama и др.) из закрытого контура компании [11.2, 14.2].
*   **Asynchronous (Асинхронность)** — способ выполнения кода, при котором тяжелые операции (например, сетевые запросы) не блокируют основной поток выполнения приложения, позволяя параллельно обрабатывать другие задачи [1.1].

### B
*   **Backpressure (Обратное давление)** — ситуация в потоках данных (Streams), когда источник (Producer) генерирует данные быстрее, чем получатель (Consumer) успевает их прочитать и обработать. Приводит к перегрузке оперативной памяти, если не контролируется.

### C
*   **CPython** — стандартная и наиболее распространенная реализация интерпретатора языка программирования Python, написанная на языке C.
*   **Claude** — семейство современных больших языковых моделей, разработанных компанией Anthropic. Известны высокой точностью рассуждений и отличной поддержкой XML-разметки промптов.

### D
*   **Dependency Injection (Внедрение зависимостей)** — паттерн проектирования, при котором класс запрашивает внешние зависимости (например, другие сервисы или адаптеры) извне, вместо того чтобы создавать их внутри себя. Обеспечивает слабую связанность компонентов [2.3].

### E
*   **Event Loop (Цикл событий)** — ядро механизма асинхронности в Node.js, отвечающее за координацию выполнения коллбэков, обработку системных прерываний от ввода-вывода (сеть, диски) и планирование задач [1.1].

### G
*   **Global Interpreter Lock (GIL)** — глобальная блокировка интерпретатора в CPython, которая гарантирует, что только один поток операционной системы может выполнять байт-код Python в каждый момент времени [1.4].

### H
*   **highWaterMark** — внутренний параметр ограничения размера буфера (в байтах) в Streams API Node.js. Служит сигнальным порогом для контроля переполнения памяти при стриминге.

### M
*   **Mock (Заглушка)** — тестовый дублер реального класса, который имитирует его поведение и возвращает заранее заготовленные, предсказуемые данные для изоляции тестируемого компонента [2.4].

### N
*   **Non-deterministic (Недетерминированность)** — свойство систем возвращать разные результаты при одинаковых входных данных (характерно для генеративных моделей ИИ) [2.1].

### P
*   **Prompt (Промпт)** — текстовый запрос, отправляемый в языковую модель ИИ для получения ответа, содержащий инструкции, контекст и входные данные [2.1].

### R
*   **Repository (Репозиторий)** — паттерн проектирования, который изолирует доменную логику от деталей реализации доступа к данным (базам данных, файловым хранилищам или векторным базам).

### S
*   **SOLID** — акроним пяти базовых принципов объектно-ориентированного программирования и проектирования классов, направленных на создание гибкого и поддерживаемого программного кода [2.1].
*   **Server-Sent Events (SSE)** — технология отправки текстовых сообщений от сервера к клиенту в режиме реального времени в рамках одного удерживаемого HTTP-соединения [10.1, 13.1].
*   **Streaming (Стриминг)** — непрерывная передача данных по частям (чанками) по мере их генерации, исключающая необходимость ожидания полной сборки пакета данных на сервере [1.1].

### T
*   **TypeScript** — строго типизированный язык программирования, развивающийся как надстройка над JavaScript, компилируемый в чистый JS для выполнения в Node.js или браузере.
*   **Time-to-First-Token (TTFT)** — метрика производительности ИИ-систем, измеряющая время от момента отправки запроса пользователем до момента получения первого сгенерированного моделью символа на клиенте.

### V
*   **Vercel AI SDK** — специализированная библиотека с открытым исходным кодом для Node.js и TypeScript, упрощающая построение интерфейсов стриминга, работы с чат-состояниями и интеграцию с облачными провайдерами моделей.
*   **V8** — высокопроизводительный движок компиляции и выполнения JavaScript/TypeScript с открытым исходным кодом, разработанный Google и лежащий в основе среды выполнения Node.js.

### X
*   **XML-теги в промптах** — структурирующие текстовые маркеры (например, `<instructions>...</instructions>`), используемые для разграничения контекста в запросах к моделям Claude. Помогают модели лучше ориентироваться в переданных данных.
