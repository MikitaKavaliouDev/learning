# ЧАСТЬ 2. Технические решения и их простые аналогии

## 1. Adaptive RAG (Query Router): Simple RAG vs. Advanced RAG

### Что вы сделали:
Вы разделили обработку запросов на два потока:
* **Simple RAG:** Для простых вопросов («Где парковка?», «Часы работы подъемника?»).
* **Advanced Hybrid RAG:** Для сложных вопросов («Возможен ли возврат ски-пасса из-за травмы на 3-й день?»).

### Почему именно так? (Инженерное обоснование):
1. **Экономия денег и времени:** 70% вопросов пользователей — простые. Прогонять их через тяжелые переранжировщики (Re-rankers) — это выброс денег и лишняя задержка в 500 мс.
2. **Точность там, где ошибаться дорого:** В 30% случаев речь идет о деньгах и правилах. Там ошибка стоит потери клиента или денег компании.

## 2. Фильтрация метаданных по `resort_id` (Metadata Pre-Filtering)

### Что вам сказал интервьюер и в чем суть:
У вас было 50–100 PDF-файлов с правилами разных курортов. Если искать векторным поиском сразу по всем 100 файлам, векторная база может случайно вытащить кусок текста из правил курорта *«Шамони»* для пользователя, который спрашивает про *«Межев»* (потому что формулировки возврата денег у них похожи на 95%).

### Как это правильно решать (Metadata Pre-Filtering):
При сохранении текста в PostgreSQL (`pgvector`) к каждому куску текста (chunk) добавляется метадата: `{ resort_id: "chamonix" }`.
При запросе мы **сначала выполняем обычный SQL-запрос**: `WHERE resort_id = 'chamonix'`, отсекая 99% ненужных документов, и **только потом** делаем векторный поиск по оставшимся 30 чанкам.

### 💡 Простая аналогия из жизни: «Архивный шкаф с папками»
> **Без фильтрации (Чистый векторный поиск):**

> **С фильтрацией по `resort_id` (Metadata Pre-Filtering):**

## 3. PostgreSQL + `pgvector` (HNSW Index) vs. Выделенная векторная БД

### Почему PostgreSQL + `pgvector`, а не Pinecone / Weaviate?
1. **Операционная простота:** Не нужно поднимать, оплачивать и поддерживать еще один сторонний сервис.
2. **Транзакции и данные в одном месте:** Пользователи, заказы и векторные эмбеддинги живут в одной БД с поддержкой ACID.
3. **Индекс HNSW (Hierarchical Navigable Small World):** Дает логарифмическую скорость поиска $O(\log N)$ и точность (Recall) > 95% без необходимости переобучать индекс при добавлении новых документов.

---

### 💡 Простая аналогия из жизни: «Швейцарский нож vs Набор узких инструментов»
> **Выделенная векторная БД (Pinecone):** 
> Это как купить отдельное профессиональное здание-склад только для того, чтобы хранить там коробку с чертежами. Каждый раз, когда вам нужен чертеж, вы садитесь в машину и едете на этот склад.
>
> **PostgreSQL + `pgvector`:**
> Это ваш основной рабочий стол (основная БД). Вы просто добавили на этот стол удобную выдвижную полку для чертежей (pgvector). Все под рукой, не нужно никуда ездить, а порядок идеальный.

## 4. Zod Schemas & Tool-Calling

### Почему вы используете Zod?
LLM по своей природе выдают свободный текст. Но бэкенд-код не может работать со свободным текстом — ему нужен четкий JSON с правильными типами данных (`number`, `boolean`, `string`).
Zod гарантирует, что модель вернет строго валидированный объект. Если модель ошиблась в формате, Zod мгновенно выбросит ошибку, и система попросит модель исправиться до выполнения кода.

---

### 💡 Простая аналогия из жизни: «Бланк на визу»
> **Свободный ответ LLM (Без Zod):**
> Вы приходите в посольство и устно рассказываете историю своей жизни. Чиновник (бэкенд) ничего не понимает, потому что ему нужно занести данные в компьютерные поля.
>
> **Строгий ответ через Zod:**
> Вам дают жесткий бланк с клеточками: *[Имя: 20 символов] [Дата рождения: ДД/ММ/ГГГГ] [Номер паспорта: цифры]*. Если вы заполнили клеточку даты словами «прошлым летом», автомат не принимает анкету и заставляет переписать ровно в формате ДД/ММ/ГГГГ.

## 5. Human-In-The-Loop (HITL) через Slack

### Что это и зачем?
Когда агент решает сделать возврат денег (финансовая операция), он **не имеет права** вызвать API возврата автоматически. Он замораживает свою сессию и отправляет интерактивное сообщение с кнопками [Одобрить] / [Отклонить] в Slack менеджеру.

---

### 💡 Простая аналогия из жизни: «Ключ старшего кассира»
> Кассир в супермаркете может сам пробить батон хлеба или узнать цену товара (Tool-calling без HITL). 
> Но когда нужно сделать **отмену чека на большую сумму** (возврат денег), кассовый аппарат блокируется и пищит. Кассир вызывает старшего кассира, тот подходит с физическим ключом, поворачивает его в замке (нажимает кнопку в Slack), и только после этого операция завершается.

## Как вы создали Golden Dataset (Датасет «золотого стандарта»)?

## Как работает LLM-as-a-Judge в CI/CD пайплайне?
При каждом коммите или изменении промпта GitLab CI запускает тесты:
1. Ваша текущая система отвечает на все 50 вопросов из датасета.
2. Вторая модель (Judge / Судья) получает на вход:
   * **Вопрос пользователя**
   * **Эталонный контекст (Ground Truth)**
   * **Сгенерированный системой ответ**
3. Модель-Судья выставляет оценки от 1 до 5 по критериям: *Faithfulness* (верность фактам), *Answer Relevance* (релевантность ответа), *Context Recall* (полнота контекста).

## 💥 ГЛАВНЫЙ ВОПРОС ИНТЕРВЬЮЕРА: 
> **«Но как вы защищаетесь от галлюцинаций самой модели-судьи (Judge Model)?»**

Если модель-судья сама начинает галлюцинировать, ваши тесты в CI/CD становятся бесполезными. Вот **4 инженерных слоя защиты**, которые вы обязаны назвать:

### Слой 1: Оценка против «Ground Truth» (Эталона), а не «по памяти»
Судья **не ищет знания в своей памяти**. Вы передаете судье **строгий эталонный ответ** из вашего Golden Dataset. Судья работает не как эксперт, а как **сравниватель текстов**. Ему нужно лишь сравнить Текст А с Текстом Б.

### Слой 2: Chain-of-Thought (Рассуждение перед оценкой)
В промпте судьи строго прописано: *«Сначала напиши пошаговые аргументы и выдели совпадения/расхождения во фактах, и только в самом конце выведи итоговый балл»*. Когда LLM заставляют рассуждать вслух перед принятием решения, вероятность галлюцинации падает на 80-90%.

### Слой 3: Зажим модели через Zod / Structured Output
Судья возвращает ответ строго по Zod-схеме с четкими критериями, а не просто свободный текст:
```typescript
const JudgeEvaluationSchema = z.object({
  factual_hallucinations_found: z.boolean(),
  missing_key_facts: z.array(z.string()),
  faithfulness_score: z.number().min(1).max(5),
  reasoning: z.string()
});
```

### Слой 4: Детерминированные проверки (Code Assertions) ДО вызова Судьи
Перед тем как вообще тратить деньги и вызывать модель-судью, ваш скрипт на TypeScript делает детерминированные проверки кодом:
* Валиден ли JSON?
* Не пустой ли ответ?
* Содержатся ли в ответе ключевые слова/артикулы (например, номер билета `TICKET-123`), найденные через Regex?
Если детерминированная проверка кодом не пройдена, тест падает **мгновенно с 0% галлюцинаций**, даже не доходя до LLM-судьи.

---

### 💡 Простая аналогия из жизни: «Строгий экзаменатор с ключом ответов»
> **Плохой Судья (Без защиты):**
> Профессор приходит на экзамен без учебника и проверяет студентов «по памяти и настроению». Он сам может что-то забыть и поставить плохую оценку за правильный ответ.
>
> **Наш защищенный Судья (Ground Truth + CoT + Zod):**
> Профессору перед экзаменом дают **официальный ключ с правильными ответами (Ground Truth)** и **жесткую ведомость (Zod)**. 
> Инструкция требует: *«Сначала подчеркни красной ручкой все несоответствия с ключом на черновике (Chain of Thought), а затем поставь галочку в соответствующей ячейке бланка»*.

# БЛОК 1. Ответ на вопрос: «Простой RAG дает шум. Как вы избежали галлюцинаций в Simple RAG?»

Интервьюер пытается ловить вас на мысли, что «Simple RAG = плохой RAG». 
Ваш ответ должен показывать: **Simple RAG был простым с точки зрения отсутствия тяжелых моделей переранжирования (Re-rankers), но НЕ «наивным» с точки зрения фильтрации и защиты промпта.**

Вот **4 инженерных приема**, благодаря которым ваш Simple RAG выдавал 0 галлюцинаций без потери скорости:

### 1. Жесткое ограничение Top-K (Top-K = 2 или 3, а не 10)
Для простых вопросов («Часы работы подъемника») не нужно передавать 10 чанков. Вы передавали всего **2–3 самых близких куска текста**. Меньше чанков = меньше шума = меньше риск галлюцинации.

### 2. Пре-фильтрация по метаданным (Metadata Pre-filtering)
Вы не искали по всей базе. Запрос пре-фильтровался по SQL-тегам (`resort_id`, `category: 'hours'`). В поиск попадали только релевантные куски.

# ЧАСТЬ 3. Почему именно HNSW индекс? (Глубокий разбор)

Для поля `embedding` мы создаем индекс **HNSW (Hierarchical Navigable Small World)**:

```sql
CREATE INDEX idx_resort_chunks_embedding_hnsw 
ON resort_knowledge_chunks 
USING hnsw (embedding vector_cosine_ops) 
WITH (m = 16, ef_construction = 64);
```

### Как физически работает HNSW?
HNSW — это многослойный граф (похожий на экспресс-лифты в небоскребе или многоуровневый список `Skip List`):

```
[ Слои графа HNSW ]

Слой 2 (Верхний):  [A] ───────────────────────────────► [Z]  (Длинные прыжки)
                    │                                    │
Слой 1 (Средний):  [A] ──────────► [M] ─────────────────► [Z]  (Средние прыжки)
                    │               │                    │
Слой 0 (Нижний):   [A] ──► [B] ──► [M] ──► [P] ──► [X] ──► [Z]  (Все векторы, точный поиск)
```

1. **Верхние слои:** Содержат редкие узлы с «длинными связями». Поисковый запрос быстро перепрыгивает через огромные области векторного пространства.
2. **Нижний слой (Layer 0):** Содержит абсолютно все векторы, соединенные с ближайшими соседями. На этом слое происходит точная донастройка.
3. **Сложность поиска:** Выполняется за логарифмическое время $O(\log N)$ вместо перебора всех элементов $O(N)$.

---

# ЧАСТЬ 4. Почему HNSW, а НЕ другие индексы и решения?

Это один из самых частых вопросов на техническом интервью.

### 1. Почему HNSW, а не Flat (Точный векторный поиск / Без индекса)?
* **Flat (Exact KNN):** Сравнивает поисковый вектор с *каждым* вектором в таблице.
* **Почему отказались:** При 100 чанках это работает быстро, но при росте базы или при 100 одновременных запросах процессор загружается на 100%, и задержка линейно растет ($O(N)$). HNSW дает задержку в несколько миллисекунд даже на миллионах векторов.

### 2. Почему HNSW, а не IVFFlat (Inverted File Flat)?
* **Как работает IVFFlat:** Делит векторное пространство на кластеры (ячейки Вороного) с помощью алгоритма k-means.
* **Главный минус IVFFlat:** Требует **предварительного обучения (Training)** на уже готовом наборе данных. Если база пустая или в нее постоянно добавляются/удаляются документы курортов, индекс IVFFlat «деградирует» и начинает пропускать релевантные данные. Его нужно постоянно пересоздавать командой `REINDEX`.
* **Почему выбрали HNSW:** HNSW **не требует обучения**. В него можно вставлять (`INSERT`), обновлять и удалять чанки на лету без потери качества поиска.

### 3. Почему PostgreSQL + `pgvector`, а не Pinecone / Weaviate / Qdrant?
* **Причина 1: Операционная простота (Zero Extra Ops).** Не нужно покупать, настраивать, мониторить и оплачивать отдельную облачную векторную БД.
* **Причина 2: Единая точка правды и ACID.** Все реляционные данные (пользователи, заказы, билеты) и векторные чанки живут в одной БД.
* **Причина 3: Отсутствие сетевых задержек (Network Hops).** Если использовать Pinecone, вам нужно сначала сделать сетевой запрос в Pinecone, получить ID, а потом сделать запрос в Postgres за метаданными. С `pgvector` всё происходит внутри одного SQL-запроса за 5 миллисекунд.

# ЧАСТЬ 5. Пошаговый разбор: Straightforward (Simple) RAG

Этот путь используется для простых вопросов («Где арендовать экипировку в Шамони?»).

```
[Запрос] ──► [Pre-Filtering SQL] ──► [HNSW Vector Search] ──► [Threshold Check] ──► [XML Prompt Envelope] ──► [Claude Haiku]
```

### Шаг 1: Классификация
Пользователь пишет: *«Где находится прокат лыж в Шамони?»*.
Router определяет категорию: `SIMPLE_INFORMATIONAL`.

### Шаг 2: Выполнение SQL-запроса с фильтрацией
Система выполняет SQL-запрос, который **сначала** отсекает другие курорты (Metadata Pre-filtering), а **затем** ищет ближайшие векторы по косинусному расстоянию (`<=>`):

```sql
SELECT content, 1 - (embedding <=> :query_embedding) AS similarity
FROM resort_knowledge_chunks
WHERE resort_id = 'chamonix'                      -- 1. Сначала жесткий SQL-фильтр
ORDER BY embedding <=> :query_embedding ASC       -- 2. Векторный поиск по HNSW
LIMIT 3;                                          -- 3. Берем только Top-3
```

### Шаг 3: Проверка порога сходства (Similarity Threshold)
Если у лучшего чанка `similarity < 0.65`, вызов LLM **отменяется**. Пользователю сразу возвращается заготовленный ответ: *«К сожалению, в базе знаний курорта Шамони нет информации по вашему запросу»*. Это дает 0% галлюцинаций.

### Шаг 4: Конструкция промпта (XML Envelope)
Если сходство `> 0.65`, Top-2 или Top-3 чанка вставляются в строгий системный промпт:

```typescript

<context>
${chunks.map(c => c.content).join('\n---\n')}
</context>

`;
```

### Шаг 5: Генерация
Запрос отправляется в **Claude 3.5 Haiku**. 
* Общее время ответа: **250–350 мс**.
* Стоимость: **микроценты**.

# ЧАСТЬ 6. Пошаговый разбор: Complex (Advanced Hybrid) RAG

Этот путь используется для сложных правил, финансовой логики и возвратов («Я купил ски-пасс на 5 дней в Шамони, но сломал ногу на 2-й день. Вернут ли деньги?»).

```
[ Запрос ]
    │
    ├──► [ Path A: Dense Vector Search (pgvector HNSW) ] ──► Top 20
    │                                                            │
    ├──► [ Path B: Sparse Keyword Search (BM25 / tsvector) ] ──► Top 20
    │                                                            │
    ▼                                                            ▼
[ Reciprocal Rank Fusion (RRF) ] ────────────────────────► Top 15 кандидата
    │
    ▼
[ Cross-Encoder Re-Ranking (Cohere / BGE-Reranker) ] ────► Top 3 супер-точных чанка
    │
    ▼
[ Claude 3.5 Sonnet + Zod Schemas ] ─────────────────────► Tool-Calling
    │
    ▼
[ Human-In-The-Loop Approval (Slack) ] ──────────────────► Финансовый возврат
```

---

### Шаг 1: Гибридный поиск (Hybrid Retrieval)
Мы параллельно запускаем два типа поиска:

1. **Dense Vector Search (Векторный поиск):** Понимает *смысл* запроса («травма», «компенсация», «больничный»). Находит 20 кандидатов.
2. **Sparse Search (BM25 / Full-Text Search в Postgres):** Понимает *точные ключевые слова* и коды («5 дней», «ски-пасс», «медицинская справка»). Находит 20 кандидатов через SQL:
   ```sql
   SELECT content FROM resort_knowledge_chunks 
   WHERE resort_id = 'chamonix' AND fts_tokens @@ to_tsquery('english', 'pass & refund')
   LIMIT 20;
   ```

---

### Шаг 2: Объединение результатов (Reciprocal Rank Fusion — RRF)
У нас есть два списка по 20 чанков. Нам нужно объединить их в один общий рейтинг. Мы используем алгоритм **RRF**:

$$RRF\_Score(d) = \frac{1}{60 + rank_{vector}(d)} + \frac{1}{60 + rank_{bm25}(d)}$$

Чанки, которые оказались высоко в *обоих* списках, получают максимальный балл. Мы отбираем **Top-15 лучших кандидатов**.

---

### Шаг 3: Переранжирование (Cross-Encoder Re-Ranking)
Почему векторов и BM25 недостаточно?
Векторные модели (Bi-Encoders) кодируют запрос и документ *отдельно*. Они не видят взаимодействия слов запроса и документа вместе.

Мы пропускаем 15 кандидатов через **Cross-Encoder (Cohere Rerank или BGE-Reranker)**:
* Cross-Encoder принимает на вход одновременно `(Запрос + Чанк)` и прогоняет их через все слои внимания (Attention).
* Он пересчитывает реальную релевантность и отсекает «мусорные» чанки.
* Из 15 кандидатов отбираются **Top-3 самых точных чанка**. Объем контекста сокращается на 70%, а точность вырастает до 98%.

---

### Шаг 4: Вызов инструмента через Zod Schema (Tool-Calling)
Очищенные Top-3 чанка и вопрос пользователя передаются в **Claude 3.5 Sonnet** с определением Zod-инструмента:

# 1. Что такое ACID?

**ACID** — это 4 фундаментальных свойства надежности транзакций в традиционных базах данных (таких как PostgreSQL). 

Когда вы говорите на интервью: *«Мы выбрали PostgreSQL, потому что нам нужны были транзакции с поддержкой ACID для совместного хранения пользователей, платежей и векторов»*, интервьюер понимает, что вы зрелый бэкенд-инженер.

буквы расшифровываются так:

* **A — Atomicity (Атомарность) — «Всё или ничего»:**
  Транзакция не может быть выполнена частично. Если в рамках одной операции нужно сделать 3 шага (например: 1. Списать деньги, 2. Создать ски-пасс, 3. Записать вектор бронирования), и на 3-м шаге произошла ошибка — база данных **откатывает весь процесс назад**. Не может возникнуть ситуации, когда деньги списались, а ски-пасс не создался.

* **C — Consistency (Согласованность):**
  База данных переходит из одного валидного состояния в другое валидное состояние. Все правила, типы данных, связи (`Foreign Keys`) и ограничения (`NOT NULL`) строго соблюдаются. Нельзя записать вектор из 100 чисел, если колонка требует 1536 измерений.

* **I — Isolation (Изолированность):**
  Параллельные транзакции не мешают друг другу. Если 100 пользователей одновременно покупают последний ски-пасс, база обработает их так, будто они стояли в одиночной очереди. Никто не купит «билет-двойник».

* **D — Durability (Надежность / Долговечность):**
  Если база ответила: *«Транзакция успешно завершена»*, эти данные зафиксированы на диске (`WAL log`). Даже если через миллисекунду у сервера выбьет электричество, после перезагрузки данные о бронировании и векторах останутся на месте.

> **💡 Простая аналогия:** ACID — это покупка билета в банкомате. Банкомат списывает деньги и выдает билет одновременно. Если в процессе выдачи билета кончилась бумага, банкомат мгновенно возвращает деньги на карту (Атомарность).

# 2. В Complex (Advanced Hybrid) RAG мы тоже делаем Metadata Pre-filtering?

**ДА, АБСОЛЮТНО!** 
Metadata Pre-filtering делается **В САМОМ НАЧАЛЕ** — **ДО** того, как запустится хоть один поисковый алгоритм.

Пре-фильтрация по `resort_id` отсекает 99% чужих документов **одновременно для обеих веток** гибридного поиска:

```
                                [ Входящий запрос: Шамони ]
                                             │
                                             ▼
                             [ Metadata Pre-Filtering SQL ]
                                WHERE resort_id = 'chamonix'
                                             │
                 ┌───────────────────────────┴───────────────────────────┐
                 ▼                                                       ▼
  [ Ветка А: Dense Vector Search ]                       [ Ветка Б: Sparse BM25 Search ]
  Ищет только среди чанков Шамони                         Ищет ключевые слова только среди
  (по косинусному расстоянию HNSW)                        чанков Шамони (по fts_tokens)
                 │                                                       │
                 ▼                                                       ▼
            Top-20 чанков                                           Top-20 чанков
                 │                                                       │
                 └───────────────────────────┬───────────────────────────┘
                                             ▼
                             [ Reciprocal Rank Fusion (RRF) ]
```

### Как это выглядит в SQL (Оба поиска фильтруют метаданные):

```sql
-- 1. Векторный поиск фильтрует по resort_id
SELECT id, content FROM resort_knowledge_chunks 
WHERE resort_id = 'chamonix' 
ORDER BY embedding <=> :query_embedding LIMIT 20;

-- 2. BM25 поиск ТОЖЕ фильтрует по resort_id
SELECT id, content FROM resort_knowledge_chunks 
WHERE resort_id = 'chamonix' AND fts_tokens @@ to_tsquery('english', 'refund') 
LIMIT 20;
```

**Вывод:** И в Simple, и в Complex RAG мы **всегда сначала делаем Pre-filtering**, чтобы не тратить ресурсы процессора на поиск среди документов других курортов.

# 3. Куда идет схема Zod и как она работает с LLM?

Вы абсолютно правы в своей интуиции, но давайте разберем **полную техническую цепочку** (от TypeScript-кода до ответа модели), чтобы вы четко объяснили это на собеседовании.

Вот 5 шагов, как схема Zod превращается в валидный ответ:

```
[ Zod Schema в TS ] ──► [ JSON Schema ] ──► [ API Parameter: tools ] ──► [ LLM Constrained Sampling ] ──► [ TS Zod.parse() ]
```

### Шаг 1: Вы объявляете схему в TypeScript
```typescript
import { z } from "zod";

const RefundResponseSchema = z.object({
  eligible: z.boolean(),
  amount: z.number(),
  reason: z.string()
});
```

### Шаг 2: Схема автоматически превращается в JSON Schema
Специальная библиотека (или SDK Anthropic/Vercel AI SDK) автоматически конвертирует схему Zod в стандартный формат **JSON Schema** (текстовое описание структуры):
```json
{
  "type": "object",
  "properties": {
    "eligible": { "type": "boolean" },
    "amount": { "type": "number" },
    "reason": { "type": "string" }
  },
  "required": ["eligible", "amount", "reason"]
}
```

### Шаг 3: Схема передается как параметр в API Bedrock / Anthropic
Она НЕ просто вставляется руками в системный промпт. Вы передаете ее в специальный аргумент запроса API — `tools` или `response_format`:

```typescript
const response = await anthropic.messages.create({
  model: "claude-3-5-sonnet-20241022",
  max_tokens: 1024,
  messages: [{ role: "user", content: "..." }],
  
  // ВОТ СУДА ПЕРЕДАЕТСЯ СХЕМА КАК ПАРАМЕТР API:
  tools: [{
    name: "process_refund_decision",
    description: "Вызови эту функцию для ответа по возврату",
    input_schema: zodToJsonSchema(RefundResponseSchema) // Передали схему
  }],
  tool_choice: { type: "tool", name: "process_refund_decision" } // Принудительный вызов
});
```

### Шаг 4: Что происходит внутри модели (Constrained Decoding)?
Провайдеры (Anthropic / AWS Bedrock / OpenAI) используют **зажим генерации (Constrained Sampling)**. 
Когда модель генерирует ответ, API провайдера анализирует переданную JSON-схему и на каждом шаге генерации **блокирует токены, которые нарушают структуру JSON**. Модель физически не может выдать кавычку там, где требуется цифра.

### Шаг 5: Динамическая валидация в TypeScript на бэкенде
Когда от модели приходит ответ в виде JSON-строки, ваш бэкенд вытаскивает аргументы и прогоняет их через метод **`RefundResponseSchema.parse()`**:

```typescript
// Получили ответ от модели
const rawJson = response.content[0].input; 

try {
  // ДИНАМИЧЕСКАЯ ВАЛИДАЦИЯ КОДОМ:
  const validatedData = RefundResponseSchema.parse(rawJson);
  
  // Теперь TypeScript 100% знает типы:
  console.log(validatedData.eligible); // boolean
  console.log(validatedData.amount);   // number
  
} catch (error) {
  if (error instanceof z.ZodError) {
    // Если модель ВСЕ-ТАКИ передала неправильный тип,
    // Zod выбрасывает ошибку, и мы можем отправить автоматический retry запрос в LLM
    console.error("LLM вернула невалидный JSON:", error.issues);
  }
}
```

# БЛОК 2. LLMOps: Стриминг (SSE), Задержки (TTFT) и Фоллбеки

На 2-м раунде вас обязательно спросят про **производительность (Performance)** и **надежность (Resilience)**.

### 1. Как совместить Стриминг (SSE) и Zod-валидацию?
Когда пользователь задает вопрос в чате, он не хочет ждать 3 секунды. Ему нужен мгновенный ответ. Для этого используется **Server-Sent Events (SSE)** — передача ответа частями (токенами).

* **Проблема:** Как валидировать JSON через Zod, если ответ приходит по частям?
* **Решение:** 
  * Для **простых текстовых ответов** мы стримим токены через SSE напрямую на фронтенд (Time To First Token — TTFT < 200мс).
  * Для **Tool-Calling и вызова функций** мы используем библиотеки парсинга частично сгенерированного JSON (например, `partial-json-parser`) или ждем полного формирования объекта на бэкенде, проверяем его через `Zod.parse()`, и только после успеха выполняем действие.

### 2. Что делать, если AWS Bedrock или API Anthropic упали? (Fallback Strategies)
В продакшене LLM-сервисы иногда выдают ошибку `503 Service Unavailable` или упираются в `Rate Limits` (429).

Ваша архитектура отказоустойчивости:
1. **Exponential Backoff с джиттером:** Если зафиксирована ошибка 429, SDK делает 3 повторные попытки с нарастающей задержкой (100мс -> 400мс -> 1600мс).
2. **Cross-Region Failover:** Если регион AWS Bedrock `eu-west-1` (Ирландия) недоступен, SDK автоматически перенаправляет запрос в резервный регион `us-east-1` (Вирджиния).
3. **Model Fallback:** Если Claude 3.5 Sonnet выдает ошибку, запрос автоматически переключается на Claude 3.5 Haiku или локальную модель.

# ЧАСТЬ 1. Где и как мы держали промпты в BaseSystem?

Мы использовали **гибридный подход** (Централизованный типизированный реестр в коде + Синхронизация с LangSmith Hub).

```
┌────────────────────────────────────────────────────────────────────────┐
│                        ХРАНЕНИЕ ПРОМПТОВ                               │
├──────────────────────────────────────┬─────────────────────────────────┤
│ 1. Git-based Registry (TypeScript)   │ 2. LangSmith Prompt Hub         │
│ • Хранение в виде чистых функций     │ • Централизованное хранение     │
│ • Жесткая типизация параметров       │ • Версионирование (v1.0, v1.1)  │
│ • Полный контроль через Git          │ • Тестирование PM без деплоя    │
└──────────────────────────────────────┴─────────────────────────────────┘
```

### 1. В коде: Централизованный Реестр Промптов (Prompt Registry)
Все промпты лежали в отдельном модуле `src/prompts/` (а не были разбросаны по сервисам). 
Каждый промпт представлял собой **чистую функцию**, которая принимала строго типизированный объект параметров (через Zod / TypeScript) и возвращала готовую структуру сообщений (`SystemMessage`, `HumanMessage`).

### 2. В облаке: LangSmith Prompt Hub
Для версионирования и совместной работы с продакт-менеджером промпты дублировались в **LangSmith Prompt Hub**. 
* Продакт-менеджер мог зайти в UI LangSmith, подправить формулировку промпта и запустить оценку против **Golden Dataset**.
* Когда новая версия промпта подтверждала рост метрик (например, точность вырастала с 92% до 96%), версия фиксировалась (например, `resort-refund-router:v2.3`) и обновлялась в коде.

# ЧАСТЬ 2. Как это было реализовано внутри SDK?

Главный принцип Enablement-команды: **Продуктовые инженеры НЕ должны вручную писать System Prompts и составлять длинные строки.**

В SDK мы реализовали **Инкапсулированное управление промптами (Prompt Encapsulation Pattern)**.

### Архитектурная схема в SDK:

```
                  Продуктовый код (Product Engineer)
                                │
                                ▼ Вызывает простую функцию
          sdk.refunds.evaluateEligibility({ userId, passId })
                                │
                                ▼
┌───────────────────────────────────────────────────────────────┐
│                           ВНУТРИ SDK                          │
│                                                               │
│  1. System Guardrails (Неизменяемое ядро безопасности)         │
│  2. Prompt Template (Шаблон из Prompt Registry)              │
│  3. Context Injection (Автоматическая подстановка XML)        │
│  4. Output Zod Schema (Принудительный формат ответа)          │
└───────────────────────────────────────────────────────────────┘
                                │
                                ▼
                      Вызов AWS Bedrock / LLM
```

```typescript
export const RefundPromptInputSchema = z.object({

export type RefundPromptInput = z.infer<typeof RefundPromptInputSchema>;

Твоя задача — проанализировать запрос пользователя на возврат билета ${input.userPassType}.

### СТРОГИЕ ПРАВИЛА БЕЗОПАСНОСТИ:
1. Отвечай ТОЛЬКО на основе блока <retrieved_context>.
2. Не гарантируй возврат средств, если это прямо не указано в правилах.
3. Если контекст пуст или неоднозначен, установи флаг requires_human_review = true.

### КОНТЕКСТ ПРАВИЛ КУРОРТА:
<retrieved_context>
${input.retrievedContext.join("\n\n")}
</retrieved_context>

### ЗАПРОС ПОЛЬЗОВАТЕЛЯ:
<user_query>
${input.userQuestion}
</user_query>
`;
};
```

#### 2. Как этот промпт вызывался внутри метода SDK:

```typescript
export class SalomonRefundModule {
  constructor(private bedrockClient: BedrockClient) {}

  async evaluateEligibility(params: { resortId: string; userQuestion: string }) {
    // 1. SDK сам делает RAG-поиск по базе
    const contextChunks = await this.retrieveContext(params.resortId, params.userQuestion);

    // 2. SDK сам собирает промпт из Реестра
    const systemPrompt = buildRefundSystemPrompt({
      resortName: params.resortId,
      userPassType: "SKI_PASS_STANDARD",
      retrievedContext: contextChunks,
      userQuestion: params.userQuestion
    });

    // 3. SDK сам отправляет запрос с Zod-схемой и бекдор-защитой
    return await this.bedrockClient.generateStructuredOutput({
      systemPrompt,
      schema: RefundResponseSchema,
      temperature: 0.0 // Для детерминированного ответа
    });
  }
}
```

# ЧАСТЬ 3. Три уровня защиты промптов в SDK (Почему это круто для Salomon)

Если на интервью спросят: *«А что, если продуктовой команде нужно добавить свое специфичное правило в промпт?»*, вы рассказываете про **3 уровня гибкости**:

1. **Защищенное Ядро (Immutable Core Guardrails):**
   Системные инструкции по безопасности, запрету галлюцинаций и XML-оболочки **зашиты в SDK навсегда**. Продуктовая команда не может их переопределить или отключить.

2. **Безопасная кастомизация (Custom Context Injection):**
   Если продуктовой команде нужно передать дополнительные инструкции, SDK предоставляет специальный опциональный параметр `customInstructions`. SDK сам оборачивает их в изолированный тег `<product_custom_instructions>`:
   ```typescript
   sdk.refunds.evaluateEligibility({
     userQuestion: "...",
     customInstructions: "Учитывать локальную акцию для жителей Анси" 
   });
   ```

3. **Версионирование промптов (Prompt Versioning):**
   Каждый промпт внутри SDK имеет версию (например, `VERSION = "2.1.0"`). Когда Enablement-команда улучшает промпт и протестировала его на Golden Datasets, обновляется версия SDK. Продуктовые команды просто обновляют версию npm-пакета, получая прирост точности **без переписывания своего кода**.

# МОДУЛЬ 1. Продвинутые техники извлечения (Advanced Retrieval)

Обычный векторный поиск ищет совпадение векторного отпечатка *Вопроса* с *Чанком*. Но что делать, если вопрос пользователя слишком короткий (например: *«Шторм возврат»*) или абстрактный?

Вот 3 техники продвинутого RAG, про которые стоит упомянуть на интервью:

---

### 1. Parent-Document / Small-to-Big Retrieval (Маленький чанк для поиска — Большой для контекста)

* **Проблема:** Если чанк слишком большой (2000 токенов), векторный поиск работает неточно, потому что вектор «размывается». Если чанк слишком маленький (100 токенов), вектор ищется отлично, но LLM не хватает контекста для ответа.
* **Решение (Parent-Child Pattern):**
  1. Мы разбиваем документ на маленькие чанки (Child Chanks — 100 токенов) и индексируем их векторы в `pgvector`.
  2. Каждый маленький чанк ссылается на ID своего родительского крупного блока (Parent Document — 1000 токенов или весь раздел).
  3. Векторный поиск ищет по **маленьким чанкам** (высокая точность), но когда релевантный маленький чанк найден, система извлекает из БД его **родительский крупный блок** и отдает в Claude 3.5 Sonnet.

```
 Документ (Parent) [1000 токенов]
 ├── Child Chunk 1 [100 токенов] ──► (Ищем вектором здесь)
 ├── Child Chunk 2 [100 токенов] ──► [Совпадение!] ──► Но отдаем в LLM весь Parent!
 └── Child Chunk 3 [100 токенов]
```

* **Аналогия:** Вы ищете книгу в библиотеке по маленькой карточке в каталоге (Child Chunk), но читать берете всю толстую книгу с полки (Parent Document).

---

### 2. HyDE (Hypothetical Document Embeddings — Гипотетические Эмбеддинги)

* **Проблема:** Вопрос пользователя (*«Сломал ногу на 2 день»*) векторно непохож на текст правила в документе (*«Раздел 4.1. Порядок выплаты компенсаций при медицинских противопоказаниях»*).
* **Решение:**
  1. Поступающий запрос пользователя сначала отправляется в легкую модель (Claude Haiku) с промптом: *«Сгенерируй гипотетический идеальный ответ на этот вопрос на основе типичных правил курорта»*.
  2. Модель генерирует галлюцинированный, но *формально правильный* гипотетический ответ.
  3. Мы векторизуем **этот гипотетический ответ** и ищем похожие векторы в `pgvector`. 
  4. Поскольку гипотетический ответ написан «языком документов», векторный поиск находит реальные правила с точностью до 95%!

---

### 3. Query Rewriting / Multi-Query Expansion (Переписывание запросов)

* **Проблема:** Пользователи пишут с опечатками, сленгом или слишком кратко.
* **Решение:** Переписывающий модуль (Query Rewriter) превращает 1 запрос пользователя в 3 вариации:
  * Исходный: *«Скипасс отмена дождь»*
  * Вариация 1: *«Какова политика возврата средств за ски-пасс при неблагоприятных погодных условиях?»*
  * Вариация 2: *«Компенсация за неиспользованные дни катания из-за дождей и закрытия подъемников»*
  Система выполняет 3 параллельных векторных поиска и объединяет результаты.

# МОДУЛЬ 2. Синхронизация векторов в реальном времени (CDC)

Интервьюер спросит: *«Что происходит, когда менеджер меняет правило в PDF-файле или обновляет цены на экипировку в основной Postgres БД? Как векторная база узнает об этом без простоя системы?»*

```
 [ PostgreSQL Main DB ] ──► [ CDC / Debezium ] ──► [ RabbitMQ / Kafka ] ──► [ Ingestion Worker ] ──► [ Update pgvector ]
   (Изменение цены/правил)      (Фиксация WAL)          (Очередь событий)       (Перерасчет вектора)      (Мгновенно обновлено)
```

### Архитектура синхронизации в реальном времени:

1. **CDC (Change Data Capture) через PostgreSQL WAL (Write-Ahead Log):**
   При изменении строки в таблице продуктов или правил PostgreSQL фиксирует изменение в системном логе. Инструмент (например, Debezium или встроенные триггеры Postgres) автоматически публикует событие `DOCUMENT_UPDATED` в очередь сообщений (RabbitMQ / Kafka / AWS SQS).

2. **Асинхронный воркер (Ingestion Worker):**
   TypeScript-сервис считывает событие из очереди, берет новый текст, разбивает на чанки, генерирует новые векторы через API эмбеддингов и обновляет записи в `pgvector`.

3. **In-place HNSW Update:**
   Благодаря свойствам индекса HNSW в `pgvector`, обновившиеся векторы перестраивают связи в графе прямо на лету **без блокировки чтения** (`No read locks`). Пользователи продолжают делать RAG-запросы без единой секунды простоя.

В каталоге E-Commerce поисковые алгоритмы имеют разные сильные стороны:

* **BM25 (Keyword Search):** Идеально ищет **точные названия брендов, артикулы и технологии**. Если пользователь ввел *"Speedcross"* или *"GTX"*, BM25 мгновенно найдет нужные карточки. Но BM25 бесполезен, если написать *"обувь для жидкой грязи"* (этих слов нет в названии).
* **HNSW Vector Search (Dense Search):** Идеально понимает **смысл и контекст** (*"обувь для бега по жидкой грязи и скользким камням"*), но может проигнорировать точную аббревиатуру технологии (*"GTX"*).

### Как работает RRF (Reciprocal Rank Fusion) для каталога:

1. **Векторный поиск (HNSW)** выдает Top-20 товаров по смыслу (`"mountain trail"`).
2. **Полнотекстовый поиск (BM25)** выдает Top-20 товаров по ключевым словам (`"Speedcross GTX"`).
3. **RRF-алгоритм** рассчитывает объединенный балл для каждого товара по формуле:

$$RRF\_Score(d) = \frac{1}{60 + rank_{vector}(d)} + \frac{1}{60 + rank_{bm25}(d)}$$

Товар, который попал на 1-е место в BM25 (потому что это *Speedcross*) и на 2-е место в Векторах (потому что он *для горных трейлов*), получает **максимальный суммарный RRF-балл** и поднимается на самый верх выдачи!

# 1. Главный принцип: Разделение Поиска и Генерации

Главная ошибка начинающих разработчиков — оценивать RAG как «черный ящик» (на входе вопрос, на выходе текст). 

Чтобы понять, почему система ответила плохо, нужно разделять оценку на два независимых этапа:
1. **Качество Поиска (Retrieval Quality):** Нашла ли система правильные документы из базы?
2. **Качество Генерации (Generation Quality):** Смогла ли LLM правильно прочитать эти документы и составить ответ?

```
               [ Входящий запрос ]
                        │
                        ▼
         ┌─────────────────────────────┐
         │  1. ПОИСК (Retrieval)       │ ──► Метрики: Context Relevance, Context Recall, MRR, NDCG
         └──────────────┬──────────────┘
                        │
                        ▼ (Найденные чанки)
         ┌─────────────────────────────┐
         │  2. ГЕНЕРАЦИЯ (Generation)  │ ──► Метрики: Faithfulness (Groundedness), Answer Relevance
         └──────────────┬──────────────┘
                        │
                        ▼
               [ Финальный ответ ]
```

---

# 2. «Триада RAG» (RAG Triad) — Стандарт индустрии

Существует общепринятый фреймворк оценки RAG (на нем строятся библиотеки **Ragas**, **TruLens**, **LangSmith**). Он состоит из трех основных метрик:

```
                      [ Вопрос пользователя ]
                             /        \
                            /          \
   1. Context Relevance    /            \   3. Answer Relevance
                          /              \
                         ▼                ▼
                [ Контекст RAG ] ────────► [ Ответ LLM ]
                                2. Faithfulness
                                (Groundedness)
```

### 1. Context Relevance (Релевантность контекста)
* **Что измеряет:** Насколько найденные чанки из базы данных действительно относятся к вопросу пользователя? Есть ли там «мусор»?
* **Зачем:** Если в контексте много мусора, LLM либо отвлечется (Lost in the Middle), либо потратит лишние токены и деньги.

### 2. Faithfulness / Groundedness (Достоверность / Заземленность)
* **Что измеряет:** Основан ли ответ LLM **ИСКЛЮЧИТЕЛЬНО** на найденном контексте? Нет ли там галлюцинаций или фактов из внешней памяти модели?
* **Зачем:** Это главная защита от финансовых и юридических рисков (например, выдумывание несуществующих условий возврата билета).

### 3. Answer Relevance (Релевантность ответа)
* **Что измеряет:** Отвечает ли сгенерированный ответ **именно на тот вопрос**, который задал пользователь?
* **Зачем:** Модель может составить идеальный текст на основе контекста, но вообще не ответить на суть проблемы (например, написать историю курорта вместо часов работы подъемника).

---

# 3. Классические метрики поиска (Retrieval Metrics)

Для оценки поискового слоя (`pgvector` + BM25 + Re-ranker) используются классические метрики из области Information Retrieval (IR):

* **Recall@K (Полнота поиска):** Попал ли релевантный документ в первые $K$ найденных чанков? (Например, был ли нужный документ в Top-3?).
* **Precision@K (Точность поиска):** Какой процент из $K$ найденных чанков действительно полезен?
* **MRR (Mean Reciprocal Rank):** На каком месте по счету оказался *первый* самый правильный документ? (Если на 1-м месте — балл 1.0, если на 2-м — 0.5, если на 3-м — 0.33).
* **NDCG (Normalized Discounted Cumulative Gain):** Учитывает не только наличие документов, но и их правильный порядок сортировки после Re-ranking.

## 1. Offline Evaluation (Тестирование в CI/CD)

Проводится **до деплоя кода в продакшн**, чтобы убедиться, что новый промпт или смена параметров chunking/embedding не ухудшили качество системы.

### Шаг 1: Создание Golden Dataset (Зологото датасета)
Вы вместе с Product Manager составляете датасет из 50–100 контрольных примеров. Каждый пример содержит:
```json
{
  "question": "Как оформить возврат билета при травме?",
  "ground_truth_context": ["Статья 4.2: При наличии медицинской справки за неиспользованные дни возвращается 60% стоимости..."],
  "ground_truth_answer": "Для возврата билета при травме необходимо предоставить медицинскую справку. Возврат составляет 60% от стоимости неиспользованных дней."
}
```

### Шаг 2: Автоматический запуск LLM-as-a-Judge
В GitLab CI / GitHub Actions запускается тестовый скрипт. Модель-Судья (Claude 3.5 Sonnet) сравнивает сгенерированные ответы системы с `ground_truth_answer` и `ground_truth_context` и выставляет баллы от 1 до 5.

### Шаг 3: Детерминированные проверки кодом (Code Assertions)
Перед вызовом LLM-Судьи TypeScript-скрипт проверяет:
* Ответ валиден по Zod-схеме?
* Время ответа не превысило лимит (например, < 1.5 сек)?
* Содержит ли ответ обязательные сущности (номер правила, ссылку на форму)?

---

## 2. Online Evaluation (Мониторинг в Продакшене)

Проводится **в реальном времени** на реальных пользователях.

1. **Неявный фидбек (Implicit Feedback):**
   * Скопировал ли пользователь ответ в буфер обмена?
   * Задал ли он уточняющий переспрос (*«Нет, ты не ответил на мой вопрос»*)?
   * Отменил ли он диалог на середине?
2. **Явный фидбек (Explicit Feedback):**
   * Лайк / Дизлайк (Thumbs up / Thumbs down).
   * Выбор причины дизлайка (*«Неточный ответ»*, *«Галлюцинация»*, *«Долго»*).
3. **Операционные метрики (Operational Metrics):**
   * **TTFT (Time To First Token):** Задержка до появления первого слова.
   * **Total Latency:** Общее время ответа.
   * **Cost Per Query:** Стоимость токенов на один запрос.
   * **Fallback Rate:** Процент запросов, закончившихся ошибкой или переключением на резервную модель.

# ЧАСТЬ 2. 5 Главных концепций TypeScript для LLM Engineer (Экспресс-ликбез)

### 2. Дженерики (Generics `<T>`) в SDK
Дженерик — это «переменная для типа». Нужен для того, чтобы ваш SDK мог принимать разные схемы от разных команд и возвращать правильный тип.

```typescript
// Обобщенный метод SDK для вызова LLM с любой Zod-схемой:
```

### ЧАСТЬ 2: Поисковый сервис (Retrieval Service: Pre-filtering + Hybrid + RRF + Re-rank)

Это ядро поиска. Мы показываем параллельный поиск в SQL (`Promise.all`), объединение RRF и переранжирование.

```typescript
export interface Chunk {
  id: string;
  content: string;
  score?: number;
}

export class RetrievalService {
  constructor(
    private db: DatabaseClient, 
    private reranker: RerankerClient
  ) {}

  async searchHybrid(filter: QueryFilter, topK: number = 3): Promise<Chunk[]> {
    // 1. Генерируем эмбеддинг очищенного запроса
    const queryEmbedding = await generateEmbedding(filter.cleanQuery);

    // 2. ПАРАЛЛЕЛЬНЫЙ ПОИСК с Pre-filtering по resortId
    const [vectorDocs, bm25Docs] = await Promise.all([
      // Векторный поиск (HNSW Index)
      this.db.query<Chunk>(`
        SELECT id, content FROM resort_knowledge_chunks
        WHERE resort_id = $1 AND category = $2
        ORDER BY embedding <=> $3
        LIMIT 20
      `, [filter.resortId, filter.category, queryEmbedding]),

      // Ключевой поиск (BM25 / Full-Text Search)
      this.db.query<Chunk>(`
        SELECT id, content FROM resort_knowledge_chunks
        WHERE resort_id = $1 AND category = $2 
          AND fts_tokens @@ to_tsquery('english', $3)
        LIMIT 20
      `, [filter.resortId, filter.category, filter.cleanQuery])
    ]);

    // 3. Объединение списков через RRF (Reciprocal Rank Fusion)
    const mergedCandidates = this.applyRRF(vectorDocs, bm25Docs);

    // 4. Cross-Encoder Re-Ranking (сокращаем 15-20 кандидатов до Top-3)
    const topChunks = await this.reranker.rerank({
      query: filter.cleanQuery,
      documents: mergedCandidates,
      topN: topK
    });

    return topChunks;
  }

  // Алгоритм RRF
  private applyRRF(vectors: Chunk[], keywords: Chunk[], k = 60): Chunk[] {
    const scores = new Map<string, { chunk: Chunk; score: number }>();

    const addRank = (docs: Chunk[]) => {
      docs.forEach((doc, rank) => {
        const current = scores.get(doc.id) || { chunk: doc, score: 0 };
        current.score += 1 / (k + rank + 1);
        scores.set(doc.id, current);
      });
    };

    addRank(vectors);
    addRank(keywords);

    return Array.from(scores.values())
      .sort((a, b) => b.score - a.score)
      .map(item => item.chunk);
  }
}
```

```typescript
export class RAGPipelineEngine {
  constructor(
    private retriever: RetrievalService,
    private llmClient: BedrockLLMClient
  ) {}

  async execute(userQuery: string, resortId: string): Promise<RAGAnswer> {
    // ШАГ 1: Извлечение метаданных и очистка запроса (Claude Haiku)

      prompt: `Извлеки параметры из запроса: "${userQuery}" для курорта ${resortId}`,
      schema: QueryFilterSchema,

    });

    // ШАГ 2: Гибридный поиск и Переранжирование
    const retrievedChunks = await this.retriever.searchHybrid(filter, 3);

    // Guardrail: Если релевантных документов нет вообще
    if (retrievedChunks.length === 0) {
      return {
        answer: "К сожалению, в базе знаний курорта нет информации по вашему вопросу.",
        citedSources: [],
        confidenceScore: 0,
        requiresHumanReview: false
      };
    }

    // ШАГ 3: Создание Промпт-Конверта (Anti-Hallucination Envelope)
    const systemPrompt = `
```
