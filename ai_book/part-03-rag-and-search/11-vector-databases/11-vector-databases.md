# Глава 11: Векторные базы данных — Склад Salomon

> **Ментальная модель:** *Организация склада готовой продукции.* Мы можем хранить коробки с обувью в общем углу главного офиса (pgvector в существующей БД), построить для них отдельный умный стеллаж на территории завода (OpenSearch в AWS) или арендовать специализированный роботизированный складской комплекс (Pinecone/Qdrant). Выбор зависит от объёмов, бюджета и требований к скорости.

---

## 11.1. Зачем нужны векторные базы данных

LLM не могут эффективно обрабатывать миллионы документов «в лоб» — контекстное окно ограничено, а стоимость токенов линейно растёт. Векторные базы данных решают проблему поиска: превращают текст в математические векторы и находят ближайшие по смыслу за миллисекунды, даже среди миллиардов записей.

**Ключевые применения в AI-инженерии:**

- Семантический поиск по базе знаний
- Кластеризация и классификация документов
- Рекомендательные системы («похожие товары»)
- Память для агентов (долгосрочное хранение контекстов сессий)
- Обнаружение аномалий (выбросы в векторном пространстве)

---

## 11.2. Индексы: HNSW против IVF

Сырой поиск по всем векторам (полное сканирование, KNN) работает за O(n·d), где n — количество векторов, d — размерность. Для 1 миллиона 768-мерных векторов один запрос занимает секунды — неприемлемо для продакшена.

Решение — **приближённый поиск ближайших соседей (ANN — Approximate Nearest Neighbor)**. Два доминирующих алгоритма:

### 11.2.1. HNSW (Hierarchical Navigable Small World)

**Ментальная модель:** *Карта метро с экспресс-линиями.* Чтобы добраться от окраины до центра, вы не едете через каждую остановку — вы садитесь на экспресс (верхний уровень иерархии), который перепрыгивает через районы, а на финальном уровне переходите на локальные линии для точной навигации.

HNSW строит многоуровневый граф:
- **Верхние уровни:** Редкие связи, длинные «прыжки» — быстро находим область
- **Нижние уровни:** Плотные связи — точный поиск внутри области

```python
# pgvector: создание HNSW индекса
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops);
```

**Характеристики HNSW:**

| Параметр | Значение | Комментарий |
|----------|----------|-------------|
| ef_construction | 200–400 | Качество построения (чем выше, тем точнее, но дольше строится) |
| ef_search | 100–400 | Качество поиска (чем выше, тем точнее, но медленнее) |
| M | 16–64 | Количество связей на узел (определяет память) |
| Скорость поиска | <10ms | Для 1M векторов, 768d |
| Потребление RAM | ~10× размер данных | См. расчёт ниже |

**Плюсы:** Очень быстрый поиск, высокая точность (recall 99%+).
**Минусы:** Огромное потребление RAM. Не влезает в память — не работает.

### 11.2.2. IVF (Inverted File Index)

**Ментальная модель:** *Библиотечный каталог.* Вместо того чтобы ходить по всем полкам, вы сначала идёте в каталог (квантование), находите раздел «Спорт — горные лыжи», а затем уже ищете конкретную книгу внутри этого раздела.

IVF разбивает векторное пространство на кластеры (ячейки Вороного). Поиск идёт только по ближайшим кластерам:

```sql
-- pgvector: создание IVF индекса
CREATE INDEX ON documents USING ivf (embedding vector_cosine_ops)
WITH (lists = 100);  -- Количество кластеров
```

**Характеристики IVF:**

| Параметр | Значение | Комментарий |
|----------|----------|-------------|
| lists | 10–1000 | Количество кластеров (sqrt(n) — эвристика) |
| probes | 1–100 | Количество кластеров для поиска |
| Скорость поиска | ~50ms | Зависит от probes |
| Потребление RAM | ~2× размер данных | Значительно меньше HNSW |

**Плюсы:** Компактный, работает на SSD.
**Минусы:** Медленнее HNSW, требует калибровки (количество кластеров и probes).

### Сравнение

| Критерий | HNSW | IVF |
|----------|------|-----|
| Скорость поиска | ⚡ Быстрый | 🐢 Медленнее в 3–10× |
| Точность (recall) | 99%+ | 95–98% (зависит от probes) |
| RAM | ~10× данных | ~2× данных |
| Настройка | Минимальная | Требует калибровки |
| Обновление (insert) | Дорогое | Дешёвое |

## 11.3. pgvector: реляционная + векторная в одном

pgvector — расширение PostgreSQL, добавляющее тип `vector(n)` и индексы для ANN-поиска.

### Установка и настройка

```sql
-- Включаем расширение
CREATE EXTENSION vector;

-- Создаём таблицу с векторным полем
CREATE TABLE product_specs (
    id SERIAL PRIMARY KEY,
    product_name TEXT NOT NULL,
    category TEXT NOT NULL,
    description TEXT,
    embedding vector(768)        -- 768-мерный эмбеддинг
);

-- Создаём HNSW индекс для быстрого поиска
CREATE INDEX idx_product_embedding
ON product_specs
USING hnsw (embedding vector_cosine_ops);
```

### Поиск с фильтрацией по метаданным

Главное преимущество pgvector — можно комбинировать векторный поиск с SQL-фильтрацией:

```sql
-- Поиск похожих товаров с фильтром по категории
SELECT
    product_name,
    category,
    1 - (embedding <=> query_embedding) AS similarity
FROM product_specs
WHERE category = 'bindings'           -- SQL-фильтр
ORDER BY embedding <=> query_embedding  -- Векторный поиск (L2)
LIMIT 10;
```

**Операторы pgvector:**

| Оператор | Метрика | Описание |
|----------|---------|----------|
| `<=>` | L2 distance | Евклидово расстояние |
| `<#>` | Negative inner product | Отрицательное скалярное произведение |
| `<=>` | Cosine distance | Косинусное расстояние (с вектором_cosine_ops) |

### Когда выбирать pgvector

- У вас уже есть PostgreSQL в инфраструктуре
- Нужна строгая согласованность данных (ACID)
- Векторы хранятся вместе с реляционными данными (размеры, цены, количество)
- Количество векторов: до 10–50 миллионов

**Ограничение:** pgvertical scaling — это вертикальное масштабирование PostgreSQL. Для >100M векторов и высокой пропускной способности нужны специализированные решения.

## 11.4. AWS OpenSearch для векторов

OpenSearch (форк Elasticsearch) поддерживает векторный поиск «из коробки», включая гибридный (kNN + BM25).

### Конфигурация индекса

```json
{
  "settings": {
    "index": {
      "knn": true,
      "knn.space_type": "cosinesimil"
    }
  },
  "mappings": {
    "properties": {
      "product_embedding": {
        "type": "knn_vector",
        "dimension": 768,
        "method": {
          "name": "hnsw",
          "engine": "lucene",
          "space_type": "cosinesimil",
          "parameters": {
            "ef_construction": 256,
            "m": 16
          }
        }
      },
      "product_name": { "type": "text" },
      "category": { "type": "keyword" }
    }
  }
}
```

### Гибридный поиск в OpenSearch

```json
{
  "size": 10,
  "query": {
    "bool": {
      "must": [
        {
          "match": {
            "product_name": "Shift 13"
          }
        }
      ],
      "filter": [
        {
          "knn": {
            "product_embedding": {
              "vector": [0.1, 0.5, ...],
              "k": 50
            }
          }
        }
      ]
    }
  }
}
```

### Когда выбирать OpenSearch

- Уже используете Elasticsearch/OpenSearch для логирования
- Нужен гибридный поиск (BM25 + векторы) в одной системе
- Требуется advanced indexing (фильтры, агрегации, фасетный поиск)
- Количество векторов: до 500 миллионов

**Недостаток:** OpenSearch — тяжёлая система (JVM, настройка шардов, GC-tuning). Операционные расходы выше, чем у pgvector.

## 11.5. Специализированные векторные БД: Pinecone, Qdrant

Pinecone и Qdrant — базы данных, спроектированные с нуля для векторов.

### Pinecone

```python
import pinecone

pinecone.init(api_key="pc-...", environment="eu-west-1")
index = pinecone.Index("salomon-products")

# Вставка векторов
index.upsert([
    {
        "id": "shift13-001",
        "values": [0.1, 0.2, ...],  # 768-мерный вектор
        "metadata": {
            "product": "Shift 13 MNC",
            "category": "bindings",
            "price": 450
        }
    }
])

# Поиск
results = index.query(
    vector=[0.1, 0.5, ...],
    top_k=10,
    filter={"category": {"$eq": "bindings"}, "price": {"$lte": 500}}
)

for match in results.matches:
    print(f"ID: {match.id}, Score: {match.score}")
```

### Когда выбирать Pinecone/Qdrant

- Нужна managed-инфраструктура («не думать о серверах»)
- >100 миллионов векторов
- Высокая пропускная способность (>1000 QPS)
- Нет существующей PostgreSQL/OpenSearch

**Недостаток:** Стоимость (Pinecone — от $0.1/час за pod). Vendor lock-in.

## 11.6. Расчёт RAM для HNSW-индекса

HNSW хранит весь граф в оперативной памяти. Формула для приблизительного расчёта:

```
RAM ≈ d × n × 4 × M × 1.5
```

Где:
- `d` = размерность вектора (768 для ada-002, 1024 для Cohere)
- `n` = количество векторов
- `M` = количество связей на узел (типично 16–64)
- `4` = размер float (4 байта)
- `1.5` = коэффициент на overhead (граф, метаданные индекса)

**Пример расчёта для 15 миллионов векторов:**

```
d = 768
n = 15,000,000
M = 32

RAM ≈ 768 × 15,000,000 × 4 × 32 × 1.5
    = 768 × 15M × 4 × 32 × 1.5
    = 2,211,840,000,000 байт
    ≈ 2.2 ТБ
```

**Почему 16 ГБ недостаточно для 15M векторов?** Даже без HNSW, простое хранение 15 миллионов 768-мерных векторов в формате float32 занимает:

```
15,000,000 × 768 × 4 = 46,080,000,000 байт ≈ 43 ГБ
```

База данных с 16 ГБ RAM физически не может удержать в памяти 43 ГБ данных. Решение: либо IVF (меньше памяти), либо сегментирование (sharding) по нескольким инстансам, либо специализированная БД (Pinecone с авто-шардированием).

## 11.8. Паттерн: мульти-уровневое хранение

В production-системах часто используется комбинация:

```
Layer 1: PostgreSQL/pgvector
  - Каталог товаров, размеры, цены (реляционные данные)
  - Векторы эмбеддингов для каждого товара
  - До 5M векторов

Layer 2: OpenSearch
  - Полнотекстовый + векторный поиск по описаниям
  - Технические спецификации, PDF-инструкции
  - До 50M векторов

Layer 3: Pinecone/Qdrant
  - Долгосрочная память агентов (миллиарды сессий)
  - Огромные коллекции отзывов, истории покупок
  - 100M+ векторов
```

## 💬 Каверзный вопрос на интервью

> *«Команда Salomon планирует проиндексировать 15 миллионов отзывов о товарах со всего мира для анализа настроений. Наш тимлид предлагает развернуть HNSW-индекс в базе PostgreSQL на инстансе с 16 ГБ RAM. Проведите технический расчёт требований к памяти для этого индекса и объясните, почему это решение приведёт к сбою базы данных под нагрузкой.»*

**Архитектурный разбор:**

1. **Расчёт памяти:** Используем эмбеддинги `int8` (8-битное квантование для экономии) или `float32`? Даже с `float32`:
   - 15M × 768 × 4 байта = 46 ГБ только на хранение векторов
   - HNSW добавляет ~10× overhead = 460 ГБ
   - Итого с M=32: более 500 ГБ RAM требуется

2. **Почему 16 ГБ RAM приведёт к сбою:** PostgreSQL будет пытаться обслуживать HNSW-индекс через дисковый кэш (OS page cache). При каждом запросе будет происходить thrashing — постоянная подкачка страниц с диска, так как 16 ГБ RAM катастрофически не хватает. CPU будет простаивать в ожидании I/O, latency запросов вырастет с миллисекунд до секунд, и БД упадёт по timeout.

3. **Альтернативы:**
   - IVF-индекс (меньше памяти): ~2× данных + lists + probes = ~100 ГБ. Всё ещё не влезает в 16 ГБ RAM, но хотя бы цена ошибки ниже.
   - Sharding: Разделить 15M отзывов на 10 шардов по 1.5M, каждый на отдельном инстансе с 64 ГБ RAM.
   - Product quantization (PQ): Сжать векторы с 768 float32 до 96 байт (в 32×). Память: 15M × 96 = 1.4 ГБ. Потеря точности — 2–5%.
   - Использовать Pinecone или Qdrant: managed-решения с автоматическим шардированием и сжатием.
