# Глава 9: Гибридный поиск и семантическое чанкование — Горная тропа

> **Ментальная модель:** *Поиск правильной тропы по карте.* У вас есть два способа ориентироваться: читать точные указатели с названиями пиков (ключевые слова) и оценивать рельеф местности вокруг (семантика). Лучший проводник использует оба метода одновременно. Чисто ключевой поиск (BM25) найдёт «крепления Shift 13» по точному совпадению, но пропустит «регулировку усиления срабатывания», а чистый семантический поиск поймёт смысл, но потеряет точный артикул.

---

## 9.1. Откуда взялся гибридный поиск

Наивный RAG (Naive RAG) работает по простой схеме: пользователь задаёт вопрос → мы превращаем его в вектор → ищем топ-K похожих векторов в базе → отправляем найденные тексты в LLM → получаем ответ. Эта схема ломается в двух типичных ситуациях:

1. **Вопрос содержит точный артикул или модель:** *«Как настроить крепления Shift 13 на вес 85 кг?»* — векторный поиск может найти документы про Shift 10 (потому что векторно они «похожи»), но не найдёт точную инструкцию для Shift 13.
2. **Вопрос перефразирован:** *«Что делать, если лыжи не держат дугу на жёстком снегу?»* — BM25 не найдёт «рекомендации по кантованию», если эти слова не совпадают дословно.

**Решение:** Комбинировать два подхода — **плотные эмбеддинги (Dense Retrieval)** для семантики и **разреженный поиск (Sparse Retrieval — BM25)** для точных совпадений. Это и есть гибридный поиск.

---

## 9.2. Векторная математика: как измеряется близость

Прежде чем говорить о гибридном поиске, нужно понять, как векторы «сравниваются».

### Косинусное сходство (Cosine Similarity)

Самая популярная метрика для эмбеддингов. Измеряет угол между векторами, игнорируя их длину:

```
cosine_similarity(A, B) = (A · B) / (||A|| × ||B||)
```

- Диапазон: от -1 до 1 (1 = одинаковое направление, 0 = ортогонально, -1 = противоположно)
- **Когда использовать:** Для эмбеддингов, нормализованных к единичной длине (text-embedding-ada-002, Cohere Embed v3)

### Скалярное произведение (Dot Product)

```
dot_product(A, B) = Σ(A_i × B_i)
```

- Без нормализации: учитывает и направление, и длину вектора
- **Когда использовать:** Когда длина вектора информативна (например, частота терма в SPLADE)

### L2-расстояние (Euclidean Distance)

```
l2_distance(A, B) = sqrt(Σ(A_i - B_i)²)
```

- Интуитивно: прямое «физическое» расстояние между точками в многомерном пространстве
- **Когда использовать:** Когда векторы образуют кластеры (например, для задач классификации)

| Метрика | Диапазон | Скорость | Чувствительность к длине вектора |
|---------|----------|----------|----------------------------------|
| Cosine Similarity | [-1, 1] | Высокая | Нет |
| Dot Product | (-∞, ∞) | Высокая | Да |
| L2 Distance | [0, ∞) | Средняя | Да |

## 9.3. BM25: классический текстовый поиск

BM25 — это эволюция TF-IDF, стандарт для поисковых систем (Elasticsearch, OpenSearch). Он оценивает релевантность документа на основе:

- **TF (Term Frequency):** Как часто слово встречается в документе (но насыщение — после определённого порога дополнительные вхождения не помогают).
- **IDF (Inverse Document Frequency):** Насколько слово редкое во всей коллекции (слова «и», «в», «на» почти ничего не значат).
- **Длина документа:** Короткие документы получают бонус (если слово найдено, оно, вероятно, важнее).

```python
# BM25 на Python для демонстрации
from rank_bm25 import BM25Okapi

corpus = [
    "Крепления Shift 13 MNC подходят для лыж с шириной талии до 110 мм",
    "Крепления Shift 10 имеют максимальное усилие срабатывания 10 DIN",
    "Настройка усиления срабатывания зависит от веса и уровня катания"
]

tokenized_corpus = [doc.split() for doc in corpus]
bm25 = BM25Okapi(tokenized_corpus)

query = "Shift 13 настройка вес"
scores = bm25.get_scores(query.split())
# [0.72, 0.31, 0.45] — первый документ самый релевантный
```

**Сильные стороны BM25:**
- Идеально для точных артикулов, моделей, имён собственных
- Мгновенный (инвертированный индекс — O(1) на терм)
- Не требует GPU для инференса

**Слабые стороны:**
- Не понимает синонимы: «горнолыжные ботинки» ≠ «ski boots»
- Терминологический разрыв: пользователь пишет «жесткие ботинки», а в документе «stiffness index = 130»

## 9.4. Плотные эмбеддинги (Dense Retrieval)

Векторный поиск решает проблему синонимов и семантической близости. Каждый документ и запрос превращаются в плотный вектор (например, 1536-мерный для `text-embedding-ada-002`).

```python
# Семантический поиск с OpenAI Embeddings
from openai import OpenAI
import numpy as np

client = OpenAI()

def embed_text(text: str) -> list[float]:
    response = client.embeddings.create(
        model="text-embedding-3-small",
        input=text
    )
    return response.data[0].embedding

query_vec = np.array(embed_text("Как настроить усилие срабатывания креплений?"))
doc_vec = np.array(embed_text("Регулировка DIN-настроек креплений Shift 13"))

# Косинусное сходство
similarity = np.dot(query_vec, doc_vec) / (
    np.linalg.norm(query_vec) * np.linalg.norm(doc_vec)
)
# 0.89 — высокая семантическая близость, хотя слова не совпадают
```

**Сильные стороны:**
- Понимает смысл, синонимы, парафразы
- Работает на нескольких языках (multilingual embeddings)
- Единое векторное пространство для всех документов

**Слабые стороны:**
- «Слеп» к точным артикулам: «Shift 13» → вектор похож на «Shift 10» и «Shift 7»
- Требует GPU или API-вызовов для инференса
- Нужен индекс (HNSW/IVF) для быстрого поиска по миллионам векторов

## 9.5. Reciprocal Rank Fusion (RRF) — объединение результатов

RRF — простой и эффективный алгоритм для комбинирования результатов из разных поисковых систем. Не требует обучения, работает на рангах:

```python
def reciprocal_rank_fusion(
    dense_results: list[dict],
    sparse_results: list[dict],
    k: int = 60
) -> list[dict]:
    """
    Объединение ранжированных списков через RRF.
    k — константа сглаживания (обычно 60).
    """
    scores = {}

    for rank, doc in enumerate(dense_results):
        doc_id = doc["id"]
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)

    for rank, doc in enumerate(sparse_results):
        doc_id = doc["id"]
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)

    # Сортируем по убыванию RRF-score
    ranked = sorted(scores.items(), key=lambda x: x[1], reverse=True)
    return [{"id": doc_id, "rrf_score": score} for doc_id, score in ranked]
```

**Почему RRF, а не взвешенная сумма?** Веса для BM25 и косинусного сходства — это гиперпараметры, которые надо подбирать под каждую коллекцию. RRF не требует настройки: он просто даёт более высокий приоритет документам, которые оба алгоритма поставили высоко.

## 9.6. Продвинутое чанкование

Наивная нарезка текста по 500 символов ломает контекст посередине предложения и смешивает разные темы в одном чанке. Для качественного RAG нужны продвинутые стратегии.

### 9.6.1. Семантический сплиттинг

Делим текст там, где резко меняется тема. Используем эмбеддинги предложений: если косинусное расстояние между соседними предложениями превышает порог, ставим разрыв:

```python
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer('all-MiniLM-L6-v2')

def semantic_chunk(text: str, threshold: float = 0.3) -> list[str]:
    sentences = text.split('. ')  # Упрощённая токенизация
    embeddings = model.encode(sentences)

    chunks = []
    current_chunk = [sentences[0]]

    for i in range(1, len(sentences)):
        similarity = np.dot(embeddings[i-1], embeddings[i]) / (
            np.linalg.norm(embeddings[i-1]) * np.linalg.norm(embeddings[i])
        )
        if similarity < threshold:
            # Тема резко изменилась — сохраняем чанк
            chunks.append('. '.join(current_chunk))
            current_chunk = [sentences[i]]
        else:
            current_chunk.append(sentences[i])

    if current_chunk:
        chunks.append('. '.join(current_chunk))

    return chunks
```

### 9.6.2. Обогащение метаданными

Каждый чанк должен содержать метаданные, которые помогут при поиске и пост-обработке:

```json
{
  "text": "Максимальное усилие срабатывания креплений Shift 13 — 13 DIN...",
  "metadata": {
    "source": "shift-13-manual.pdf",
    "page": 12,
    "section": "Технические характеристики",
    "product_model": "Shift 13",
    "product_category": "крепления",
    "language": "ru"
  }
}
```

**Критическое правило:** Метаданные должны участвовать в поиске, но не должны быть единственным критерием. Иногда самая релевантная информация лежит в документе без точного совпадения метаданных.

### 9.6.3. Извлечение табличных данных

PDF-инструкции Salomon содержат таблицы размеров, весов, DIN-настроек. Стандартный текст-сплиттер превращает таблицу в бессвязный набор чисел. Решение — парсить таблицы отдельно и сохранять как структурированные чанки:

```python
import pdfplumber

def extract_tables_from_pdf(pdf_path: str) -> list[dict]:
    tables = []
    with pdfplumber.open(pdf_path) as pdf:
        for page_num, page in enumerate(pdf.pages):
            for table in page.extract_tables():
                # Преобразуем таблицу в Markdown-формат
                md_table = []
                for row in table:
                    md_table.append("| " + " | ".join(row) + " |")
                tables.append({
                    "text": "\n".join(md_table),
                    "metadata": {
                        "source": pdf_path,
                        "page": page_num + 1,
                        "type": "table"
                    }
                })
    return tables
```

## 9.7. Parent-Document Retriever: концепция

Разделение репрезентации документа для **поиска** и для **генерации**:

1. **Для поиска (Child Chunks):** Мелкие чанки по 100–200 токенов. Векторный поиск по ним максимально точен.
2. **Для генерации (Parent Documents):** Крупные блоки — вся страница или раздел целиком. Содержат достаточно контекста для LLM.

```
┌─────────────────────────────────────────────┐
│         Parent Document (страница)           │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐    │
│  │ Child 1  │ │ Child 2  │ │ Child 3  │    │
│  │ (200 tok)│ │ (200 tok)│ │ (200 tok)│    │
│  └────┬─────┘ └────┬─────┘ └────┬─────┘    │
│       │             │             │          │
│       ▼             ▼             ▼          │
│  Векторный индекс → поиск по мелким чанкам  │
│         │                                    │
│         ▼                                    │
│  Найден Child 2 → возвращаем Parent целиком  │
└─────────────────────────────────────────────┘
```

Конкретная реализация будет подробно разобрана в Главе 10 (Реранкинг).

## 💬 Каверзный вопрос на интервью

> *«Пользователь ищет в базе знаний Salomon: "Как настроить крепления Shift 13 на вес 85 кг?". Модель находит статьи о креплениях Shift 10 и статьи о настройке веса для ботинок, но выдаёт опасный галлюцинированный ответ. Как изменить стратегию чанкования и метаданных исходных PDF-инструкций, чтобы гарантировать точное попадание в контекст?»*

**Архитектурный разбор:**

1. **Проблема:** Векторный поиск не видит разницы между «Shift 13» и «Shift 10», потому что эмбеддинги семантически похожи. BM25 находит фрагмент про вес, но он относится к ботинкам, а не к креплениям.

2. **Решение по чанкованию:** Каждый чанк должен содержать **заголовок раздела и модель продукта** в самом тексте (не только в метаданных), чтобы BM25 мог их найти:
   - Плохой чанк: «Максимальное усилие — 13 DIN»
   - Хороший чанк: «Крепления Salomon **Shift 13**. Максимальное усилие срабатывания — 13 DIN»

3. **Решение по метаданным:** Ввести поля `product_model` и `compatible_models` для фильтрации до поиска. При запросе парсить явное упоминание модели NER-моделью (`"Shift 13"`) и добавлять фильтр в векторный поиск.

4. **Гибридный поиск:** Объединить BM25 (находит Shift 13 по точному совпадению) и Dense (находит «настройка усилия» по смыслу) через RRF. Child Chunks нарезать семантически (по 200 токенов), а Parent возвращать целой страницей, чтобы у LLM был полный контекст.
