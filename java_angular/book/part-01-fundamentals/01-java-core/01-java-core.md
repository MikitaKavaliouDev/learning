## 1.1 Типы, компиляция и JVM

### Жизненная аналогия

Представьте, что вы пишете книгу. **Java** — это как написать книгу, затем отдать её редактору, который тщательно проверит каждую букву, переведёт на другой язык и только потом отправит в печатный станок (JVM). **JavaScript/Python** — это устный синхронный перевод: слова произносятся и сразу же интерпретируются, ошибки всплывают уже в процессе разговора.

### Техническая глубина

Код на Java компилируется в байт-код (файлы `.class`), который затем выполняется виртуальной машиной Java (JVM). Это обеспечивает кроссплатформенность: «Написано однажды — работает везде».

В отличие от TypeScript, где типы «стираются» в рантайме, в Java типы существуют на протяжении всего времени выполнения программы. JVM строго следит за соответствием типов и не позволит записать некорректный объект в память.

#### Примитивы и ссылочные типы

Java делит типы на две категории:
- **Примитивы** (`int`, `boolean`, `double`, `char` и др.) — хранятся в стеке, работают максимально быстро, не могут быть `null`.
- **Ссылочные типы** (`Integer`, `Boolean`, `String`, массивы, классы) — хранятся в куче (Heap), доступны через ссылки, могут быть `null`.

| Характеристика | Примитив | Объект-обёртка |
|:---|:---:|:---:|
| Хранение | Стек (если локальная переменная) | Куча (Heap) |
| Может быть null | Нет | Да |
| Скорость | Высокая | Ниже (autoboxing/unboxing) |
| Использование в коллекциях | Нет (нужна обёртка) | Да |

> **Подводный камень (Gotcha):** Сравнение объектов-обёрток через `==` сравнивает ссылки в памяти, а не значения. Для сравнения по значению всегда используйте `.equals()`. Например, `new Integer(100) == new Integer(100)` — `false`.

#### Номинальная типизация

Java использует **номинальную типизацию**: класс должен явно указать `implements SomeInterface`. Простого совпадения структуры методов недостаточно.

> **Аналогия:** Паспортный контроль в аэропорту. Вам нужен документ именно государственного образца (явное объявление implements). TypeScript использует структурную типизацию (duck typing) — если структура совпадает, объект подходит — это как фейсконтроль в клубе, где главное быть в белых кроссовках.

> **Gotcha:** Даже если класс в Java имеет один в один те же методы, что описаны в интерфейсе, компилятор выдаст ошибку, если в заголовке класса не прописано явное наследование или реализация.

### Stack и Heap

Память Java-приложения делится на две основные области:

- **Stack (Стек):** Очень быстрая память, работающая по принципу LIFO. Хранит вызовы методов и локальные переменные (примитивы и ссылки на объекты). Как только метод завершается, его память в стеке мгновенно очищается.
- **Heap (Куча):** Общий пул памяти, где физически создаются все объекты через `new`. Очищается сборщиком мусора (Garbage Collector).

> **Gotcha:** Если вы бесконечно добавляете объекты в список и GC не может их удалить (так как на них есть живые ссылки), наступает `OutOfMemoryError: Java heap space`.

## 1.2 OOP: Overloading vs Overriding

### Жизненная аналогия

**Surcharge (Overloading / Перегрузка):** Представьте **кофемашину**. На ней есть несколько кнопок «Приготовить кофе»:
- Если вы нажимаете кнопку без параметров — она наливает обычный эспрессо.
- Если передаёте параметр `молоко` — делает капучино.
- Если передаёте `молоко` и `сироп` — делает карамельный латте.

Кофемашина ещё на заводе (этап компиляции) точно знает, какой внутренний рецепт привязать к конкретному набору параметров.

**Redéfinition (Overriding / Переопределение):** Представьте сетевой отель **Ibis**. В главном офисе прописано правило: «Каждый отель обязан подавать *Стандартный завтрак*». Но когда вы приезжаете в отель в Париже — вам подают круассаны и сыр, а в Токио — рис и мисо-суп. Метод называется одинаково, но результат выясняется только при заселении (runtime).

### Техническая глубина

| Характеристика | Overloading | Overriding |
|:---|:---|:---|
| Где происходит | В рамках одного класса | В иерархии наследования |
| Сигнатура | Разные параметры (тип/количество) | **Точно такая же** сигнатура |
| Время разрешения | Компиляция (статический полиморфизм) | Выполнение (динамический полиморфизм) |
| Возвращаемый тип | Не является частью сигнатуры | Должен быть совместимым (ковариантным) |

> **Overloading:** Возвращаемый тип **не является** частью сигнатуры. Вы не можете перегрузить метод, изменив только возвращаемое значение — компилятор выдаст ошибку.

> **Overriding:** Аннотация `@Override` не обязательна для компилятора, но крайне важна: она защищает от опечаток. Если вы ошибётесь в сигнатуре, компилятор сразу укажет на ошибку, так как не найдёт метода в родителе.

### Подводные камни

**Почему в Java нет опциональных параметров, как в JavaScript?**

В Java на уровне языка нет необязательных параметров. Если вы объявили метод с двумя параметрами, вы **обязаны** передать ровно два аргумента. Overloading элегантно решает эту проблему через паттерн **Telescoping Methods**:

```java
public void makeCoffee() {
    makeCoffee(null, null);
}

public void makeCoffee(Milk milk) {
    makeCoffee(milk, null);
}

public void makeCoffee(Milk milk, Syrup syrup) {
    // Основная логика
}
```

Для большого количества параметров используйте **Builder** (через Lombok `@Builder`) или **Parameter Object** (Record).

## 1.3 OOP: Abstract Class vs Interface

### Жизненная аналогия

**Интерфейс (Interface):** Это **водительские права** или **разъём USB**. Права говорят: «Неважно кто ты — человек, робот или инопланетянин, если хочешь водить машину — ты обязан уметь *рулить*, *тормозить* и *парковаться*». Это контракт на поведение (*can-do*).

**Абстрактный класс (Abstract Class):** Это **чертёж млекопитающего** или **базовая модель автомобиля**. У любого авто есть металлический кузов, цвет, объём бака и VIN-номер (состояние/поля). Вы не можете купить «просто автомобиль» (нельзя создать экземпляр через `new`). Вы покупаете конкретный Peugeot 208, построенный на базе чертежа. Это наследование сущности (*is-a*).

### Техническая глубина

| Критерий | Abstract Class | Interface |
|:---|:---|:---|
| Состояние (поля) | Может хранить любые поля (private, protected, изменяемые) | Только `public static final` константы |
| Конструкторы | Может иметь конструкторы | Не может |
| Множественное наследование | Только один (`extends`) | Можно много (`implements`) |
| `default` методы (Java 8+) | Нет необходимости | Есть |
| `private` методы (Java 9+) | Есть всегда | Добавлены в Java 9 |
| Семантика | «Is-a» (сущность) | «Can-do» (поведение/контракт) |

> **Gotcha:** Даже с появлением `default` и `static` методов в интерфейсах (Java 8+), интерфейс **не стал** абстрактным классом, так как он всё ещё лишён возможности хранить переменные экземпляра (состояние).

## 1.4 Access Modifiers (private / default / protected / public)

### Жизненная аналогия (Многоэтажный офис корпорации)

Представьте здание крупной французской компании:

- **private:** Ваш **личный рабочий блокнот** или пароль от компьютера. Доступ имеете только вы (текущий класс).
- **default (package-private):** **Кофемашина в кабинете вашего отдела** (пакет). Коллеги из вашей комнаты могут ей пользоваться, но другие этажи — нет.
- **protected:** **Внутренняя база знаний компании**. Доступ у всех в отделе, а также у **детей основателя** (дочерние классы), даже если они работают удалённо.
- **public:** **Ресепшен на входе**. Любой прохожий с улицы может обратиться и получить информацию.

### Техническая глубина

| Модификатор | Внутри класса | Внутри пакета | Дочерние классы (другой пакет) | Везде |
|:---|:---:|:---:|:---:|:---:|
| `private` | ✅ | ❌ | ❌ | ❌ |
| `default` (без модификатора) | ✅ | ✅ | ❌ | ❌ |
| `protected` | ✅ | ✅ | ✅ | ❌ |
| `public` | ✅ | ✅ | ✅ | ✅ |

> **Gotcha:** Уровень `default` применяется автоматически, если не указан ни один модификатор. `protected` отличается от `default` тем, что даёт доступ дочерним классам из других пакетов.

## 1.5 Collections: List, Set, Map

### Жизненная аналогия

- **List (Список):** Упорядоченная очередь в кассу. У каждого элемента есть номер (индекс). Элементы могут повторяться.
- **Set (Множество):** Список уникальных гостей на вечеринке. Каждый гость может быть только один раз, порядок не гарантирован.
- **Map (Словарь):** Номерки в гардеробе. По номерку (ключ) вы получаете свою вещь (значение). Ключи уникальны.

### Техническая глубина

```java
// List — упорядоченная коллекция с дубликатами
List<String> names = new ArrayList<>();  // Быстрый доступ по индексу
List<String> linked = new LinkedList<>(); // Быстрые вставки/удаления

// Set — уникальные элементы
Set<String> uniqueNames = new HashSet<>();  // O(1) на основе hashCode()
Set<String> sorted = new TreeSet<>();       // Отсортировано

// Map — ключ → значение
Map<String, Integer> ages = new HashMap<>(); // O(1) на основе hashCode()
```

> **Gotcha:** Коллекции работают только со ссылочными типами. Нельзя создать `List<int>`, нужно `List<Integer>`. `HashSet` и `HashMap` требуют корректной реализации `equals()` и `hashCode()` у объектов-ключей. Если переопределить только `equals()`, но не `hashCode()`, объекты будут считаться разными в `HashSet`, что приведёт к дубликатам.

## 1.6 Streams API

### Жизненная аналогия

**Заводской конвейер:** Сырьё движется по ленте, проходя этапы сортировки (filter), обработки (map) и упаковки в коробку (collect). Операторы можно добавлять последовательно, но конвейер не запустится, пока не нажат финальный рубильник (терминальный оператор).

### Техническая глубина

До Java 8 обработка коллекций была императивной и громоздкой:

```java
// Старый стиль (без стримов)
List<String> activeEmails = new ArrayList<>();
for (User user : users) {
    if (user.isActive()) {
        activeEmails.add(user.getEmail());
    }
}
```

Современный Streams API (Java 8+) — это перенос функционального стиля из JavaScript/Python в Java:

```java
List<String> activeEmails = users.stream()
    .filter(User::isActive)        // Фильтрация
    .map(User::getEmail)           // Преобразование
    .collect(Collectors.toList()); // Сбор результата
```

**Популярные операторы:**
- **Промежуточные (lazy):** `filter()`, `map()`, `flatMap()`, `distinct()`, `sorted()`, `limit()`, `skip()`
- **Терминальные:** `collect()`, `toList()`, `forEach()`, `count()`, `anyMatch()`, `findFirst()`, `reduce()`

> **Gotcha:** Вычисления в стримах **ленивые**. Фильтрация и маппинг не начнут выполняться, пока в конце цепочки не будет вызван терминальный оператор (например, `.toList()` или `.collect()`).

### Пример: задача "Температуры" (CodinGame)

```java
public static int computeClosestToZero(int[] ts) {
    if (ts == null || ts.length == 0) return 0;

    return Arrays.stream(ts)
        .boxed()
        .min((a, b) -> {
            int absA = Math.abs(a);
            int absB = Math.abs(b);
            if (absA == absB) return Integer.compare(b, a);
            return Integer.compare(absA, absB);
        })
        .orElse(0);
}
```

## 1.7 Исключения (Exceptions)

### Жизненная аналогия

Представьте, что вы — пилот самолёта (ваша программа). В полёте может случиться разное:
- **Checked Exception (проверяемое):** Отказ одного из двигателей. Производитель самолёта **обязал** вас иметь план действий на этот случай. Если плана нет — вас не выпустят на взлётную полосу (код не скомпилируется).
- **Runtime Exception (непроверяемое):** Вам на голову упал чемодан с верхней полки. Производитель не мог предусмотреть все возможные чемоданы в мире. Если это случилось — программу нужно экстренно чинить.
- **Error:** Разгерметизация салона. Бортпроводники (JVM) сами выбрасывают кислородные маски (Error), пилоту остаётся только падать.

### Техническая глубина

Иерархия исключений в Java:

```
Throwable
 ├── Error (непредсказуемые системные ошибки — OutOfMemoryError, StackOverflowError)
 └── Exception
      ├── RuntimeException (NPE, IllegalArgumentException, IndexOutOfBounds)
      └── Checked Exception (IOException, SQLException, ClassNotFoundException)
```

**Checked vs Unchecked:**

```java
// Checked — компилятор заставляет обработать
public void readFile() throws IOException {
    BufferedReader br = new BufferedReader(new FileReader("file.txt"));
    // ...
}

// Unchecked — можно не обрабатывать, но лучше перехватить
public void process(String input) {
    if (input == null) {
        throw new IllegalArgumentException("Input must not be null");
    }
}
```

### Try-With-Resources (Java 7+)

До Java 7 закрытие ресурсов было ручным и подверженным ошибкам:

```java
// Старый стиль (до Java 7) — много бойлерплейта
BufferedReader br = null;
try {
    br = new BufferedReader(new FileReader("file.txt"));
    System.out.println(br.readLine());
} finally {
    if (br != null) br.close();
}
```

Современный подход:

```java
// Ресурс закроется автоматически, даже если произойдёт ошибка
try (BufferedReader br = new BufferedReader(new FileReader("file.txt"))) {
    System.out.println(br.readLine());
}
```

> **Gotcha:** Для использования в try-with-resources класс должен реализовать интерфейс `AutoCloseable`.

## 1.8 Generics

### Жизненная аналогия

Представьте коробку для перевозки. Если коробка подписана «Хрупкое стекло» (`List<Glass>`), грузчик знает, что внутрь можно класть только стекло. Если коробка подписана просто «Вещи» (`List` — raw type), туда можно положить и кирпич, и стекло, что приведёт к хаосу.

### Техническая глубина

Дженерики позволяют создавать классы, интерфейсы и методы с параметризованными типами:

```java
// Без дженериков — опасный код
List list = new ArrayList();
list.add("hello");
list.add(123); // Случайно положили число
String s = (String) list.get(1); // ClassCastException в рантайме!

// С дженериками — безопасно
List<String> list = new ArrayList<>();
list.add("hello");
// list.add(123); // Ошибка компиляции!
```

### Diamond Operator (`<>`)

До Java 7 приходилось дублировать типы:

```java
// Старая Java (до 7)
Map<String, List<String>> map = new HashMap<String, List<String>>();
```

Начиная с Java 7, компилятор научился выводить типы:

```java
// Современная Java — Diamond Operator
Map<String, List<String>> map = new HashMap<>();
```

### Wildcards (Ковариантность и Контравариантность)

Wildcards (`?`) в Java решают проблему, которую многие разработчики даже не замечают, пока не получат ошибку компиляции: **дженерики инвариантны**. Это значит, что `List<Integer>` — это **не** `List<Number>`, даже несмотря на то, что `Integer` наследуется от `Number`. Wildcards добавляют гибкости туда, где инвариантность мешает.

#### Жизненная аналогия

**Ящики с инструментами.** Представьте три типа ящиков:

*   **Инвариантный ящик:** Ящик, помеченный «Только молотки». Вы можете положить туда только молоток. Вы **не можете** поставить этот ящик на полку, где принимают ящики «Только инструменты» — этикетка должна совпадать точно.
*   **Ковариантный ящик (? extends):** Ящик, помеченный «Только то, что является инструментом / или его подтипом» (`? extends Tool`). Вы можете положить туда молоток (`Hammer extends Tool`) или отвёртку (`Screwdriver extends Tool`). Вы **можете читать** содержимое, зная, что это точно какой-то инструмент. Но вы **не можете положить** новый инструмент внутрь — вы не знаете, молотки там или отвёртки.
*   **Контравариантный ящик (? super):** Ящик, помеченный «Только то, что является предком молотка / или им самим» (`? super Hammer`). Вы можете положить туда молоток, инструмент или даже `Object`. Вы **можете положить** молоток внутрь, потому что ящик точно поддерживает молоток. Но вы **не можете гарантировать**, что, читая из него, вы получите именно молоток — может быть любой предок.

#### Техническая глубина

В Java дженерики инвариантны по умолчанию:

```java
List<Integer> ints = new ArrayList<>();
// List<Number> nums = ints; // ОШИБКА КОМПИЛЯЦИИ — инвариантность!

List<Number> nums = new ArrayList<>();
nums.add(42);       // Хорошо — int в Number
nums.add(3.14);     // Хорошо — double в Number
```

Wildcards добавляют вариантивность:

```java
// ─── Ковариантность (? extends) ───
// Producer — только читаем
List<? extends Number> numbers = new ArrayList<Integer>();
Number num = numbers.get(0);     // ✅ Читать можно — знаем что это Number
// numbers.add(42);              // ❌ Писать нельзя — может быть List<Double>

// ─── Контравариантность (? super) ───
// Consumer — только пишем
List<? super Integer> ints = new ArrayList<Number>();
ints.add(42);                    // ✅ Писать можно — Integer пройдёт
// Integer i = ints.get(0);      // ❌ Читать нельзя — может быть Object
Object obj = ints.get(0);        // ✅ Только как Object
```

#### Правило PECS (Producer Extends, Consumer Super)

Это правило — **главное, что нужно запомнить для Senior-интервью**:

| Роль | Wildcard | Можно читать | Можно писать |
|------|----------|-------------|-------------|
| **Producer** (читаем данные) | `? extends T` | ✅ `T` | ❌ |
| **Consumer** (кладём данные) | `? super T` | ❌ | ✅ `T` |
| **Producer & Consumer** | Без wildcard | ✅ `T` | ✅ `T` |

Пример из реального кода — метод, копирующий элементы из одного списка в другой:

```java
public static <T> void copy(List<? extends T> source,  // Producer — читаем
                             List<? super T> dest)     // Consumer — пишем
{
    for (T item : source) {
        dest.add(item);
    }
}

// Использование:
List<Integer> src = List.of(1, 2, 3);
List<Number> dst = new ArrayList<>();
copy(src, dst);  // ✅ Ковариантность + Контравариантность
```

#### Почему Java выбрала инвариантность?

Массивы в Java **ковариантны** (это было ошибкой дизайна):

```java
Integer[] intArr = new Integer[10];
Number[] numArr = intArr;  // ✅ Массивы ковариантны — ошибка в рантайме!
numArr[0] = 3.14;          // 💥 ArrayStoreException в runtime
```

Дженерики исправляют эту ошибку — они инвариантны, что гарантирует **типобезопасность на этапе компиляции**, а не в рантайме.

> **Gotcha #1:** Wildcard не может быть использован на верхнем уровне объявления — только для переменных, параметров методов и возвращаемых типов. Нельзя написать `class Box<? extends Number>`.
>
> **Gotcha #2:** Из-за стирания типов (Type Erasure) информация о дженериках недоступна в рантайме. Нельзя сделать `new T()`, `instanceof List<String>` или создать массив дженериков: `new List<String>[10]` — ошибка компиляции.
>
> **Gotcha #3:** `List<?>` — это unbounded wildcard. Он означает «список чего-угодно». Его можно читать только как `Object`, и нельзя ничего добавить (кроме `null`). На собеседовании спросят разницу между `List<?>` и сырым `List` (raw type). Ответ: `List<?>` типобезопасен — компилятор не позволит положить туда случайный объект, в отличие от `List`.

## 1.9 Records

### Жизненная аналогия

**Запечатанная на заводе посылка** с жёстко зафиксированным содержимым. Её нельзя вскрыть и изменить — только прочитать что внутри.

### Техническая глубина

`record` — это неизменяемый (immutable) контейнер данных, введённый в Java 14 (стабилизирован в Java 16):

```java
public record UserDTO(Long id, String email, String name) {}
```

Эта одна строка автоматически генерирует:
- Канонический конструктор со всеми полями
- Геттеры (без приставки `get` — просто `id()`, `email()`, `name()`)
- `equals()` и `hashCode()` на основе всех полей
- `toString()`

**Полный аналог вручную:**

```java
// То же самое без record — ~50 строк бойлерплейта
public final class UserDTO {
    private final Long id;
    private final String email;
    private final String name;

    public UserDTO(Long id, String email, String name) {
        this.id = id;
        this.email = email;
        this.name = name;
    }

    public Long id() { return id; }
    public String email() { return email; }
    public String name() { return name; }

    @Override public boolean equals(Object o) { /* ... */ }
    @Override public int hashCode() { /* ... */ }
    @Override public String toString() { /* ... */ }
}
```

> **Gotcha:** Records **нельзя** использовать как Entity-классы в Hibernate! Hibernate требует изменяемости для dirty checking и создания динамических прокси. Records неизменяемы и не имеют сеттеров.

## 1.10 Многопоточность и Virtual Threads

### Жизненная аналогия

**Традиционная Java (Thread-per-request):** Ресторан, где у каждого столика есть свой личный официант (один поток ОС на один запрос). Если столик думает над меню — официант стоит рядом и ждёт (блокирующий поток). Официанты — дорогой ресурс.

**Node.js (Event Loop):** Один суперэффективный официант. Он быстро принимает заказы и отдаёт их на кухню. Если кухня занята — он не ждёт, а идёт к следующему столику.

**Virtual Threads (Project Loom):** Ресторан нанимает актёров, которые мгновенно меняют маски. Если гость читает меню — «актёр» переключается на обслуживание соседа, не тратя время. Миллионы запросов с минимальным расходом памяти.

### Техническая глубина

**Проблема традиционных потоков:**
- Поток ОС — тяжёлый ресурс (~1 МБ памяти)
- Нельзя создать 100 000 потоков на сервере
- При блокировке (ожидание БД) поток ОС простаивает и ест память

**Решение — Virtual Threads (Java 21+):**

Виртуальные потоки разделяют понятие «поток в коде Java» и «физический поток ОС»:

```java
// Создание виртуального потока
Thread.startVirtualThread(() -> {
    // Блокирующая операция — не блокирует поток ОС!
    String result = jdbcTemplate.queryForObject(...);
    System.out.println(result);
});
```

- JVM может создать **миллионы** виртуальных потоков (весят ~несколько сотен байт)
- При блокировке виртуальный поток «паркуется» в памяти, а физический поток ОС переключается на другой активный виртуальный поток
- Позволяет писать синхронный код, который работает так же эффективно, как асинхронный `async/await` в Node.js

> **Gotcha:** Virtual Threads не панацея. Они не ускоряют CPU-интенсивные задачи (рендеринг, шифрование) — только ожидание I/O. Для CPU-bound задач используйте пулы платформенных потоков.

### `equals()` и `hashCode()` — почему их нужно переопределять вместе?

Представьте двух человек с одинаковыми паспортными данными. Если у них разные номера паспортов (`hashCode`), система будет считать их разными людьми, даже если имена совпадают (`equals`). В `HashSet` и `HashMap` объект ищется сначала по `hashCode()` (как по номеру шкафчика), а затем по `equals()` (проверка содержимого внутри).

Если переопределить только `equals()`, но не `hashCode()`, два «равных» объекта могут оказаться в разных «шкафчиках», и `HashSet` будет хранить дубликаты.

## Резюме главы

Java Core — это фундамент, на котором строится всё остальное. Ключевые точки для запоминания:

1. **Типы — строгие и существуют в рантайме**, в отличие от TypeScript
2. **Overloading** (компиляция) vs **Overriding** (рантайм) — два вида полиморфизма
3. **Interface** (can-do, поведение) vs **Abstract Class** (is-a, сущность с состоянием)
4. **4 уровня доступа** — от private до public, каждый со своей зоной видимости
5. **Коллекции** — List, Set, Map — требуют корректных `equals()` и `hashCode()`
6. **Streams API** — ленивый функциональный конвейер
7. **Records** — неизменяемые контейнеры (DTO), **не для JPA**
8. **Virtual Threads** — революция в многопоточности, миллионы лёгких потоков
