# Глава 5: Agile-процессы в контексте миграции

> «Миграция — это не проект с фиксированной датой. Это эволюция системы, которая должна продолжаться без остановки бизнеса» — *говорят Senior-архитекторы на собеседованиях.*

Когда вы рассказываете на интервью про миграцию длительностью 2.5 года, интервьюер неизбежно спросит: **«Как вы организовали процесс? Почему Scrum, а не Waterfall? Как вы резали монолит спринтами?»**

Эта глава даёт готовые формулировки и инструменты для ответа на такие вопросы.

---

## 5.1. Почему Scrum (не всегда) подходит для миграции

Классический Scrum предполагает неизменную скорость команды (velocity), равномерные спринты и поставку business value каждые 2 недели. В миграции это работает плохо:

| Фактор | Scrum (для новых фич) | Миграция |
|--------|----------------------|----------|
| **Неопределённость** | Низкая — требования известны | Высокая — в legacy-коде всегда сюрпризы |
| **Business value** | Виден каждый спринт | Виден только после полного перехода |
| **Приоритеты** | Product Owner диктует | Tech Lead диктует (технический долг) |
| **Риски** | Умеренные | Критические (регрессия полной системы) |
| **Демо** | Понятно заказчику | Сложно показать «мы заменили Hibernate 5 на 6» |

### Как мы адаптировали Scrum для миграции

Мы не отказались от Scrum полностью, но **модифицировали** его:

1. **Sprint длиной 2 недели** — внутри спринта команда чередовала миграционные задачи и бизнес-фичи (соотношение 70/30).
2. **Не выделяли отдельную «команду миграции»** — это страшно демотивирует разработчиков. Миграция была частью BAU (Business As Usual).
3. **Tech Lead выступал в роли PO** для миграционного бэклога.
4. **Каждый спринт содержал «окно стабилизации»** — 1 день на фикс регрессии после миграционных изменений.

## 5.2. Декомпозиция миграции на User Stories

Разбить миграцию монолита на user stories — нетривиальная задача. Нельзя просто написать «Migrate Java 8 to 21». Декомпозиция строится по **вертикальным срезам**:

### Принцип вертикального разреза

Каждая user story затрагивает **один функциональный модуль** целиком (от БД до UI):

```
User Story: "Как пользователь, я хочу просматривать список заказов на новой версии Angular"
  ├── Backend: Вырезаем модуль заказов в отдельный микросервис (Java 21)
  ├── Frontend: Создаём standalone-компонент OrderListComponent
  ├── API: Настраиваем Gateway для маршрутизации /api/orders на новый сервис
  └── Test: Интеграционные тесты (Testcontainers) + E2E (Cypress/Playwright)
```

### Инструмент декомпозиции: Event Storming

Для выделения границ модулей мы провели **Event Storming**-сессии с участием бизнес-аналитиков и разработчиков. Результат — карта доменных событий, на основе которых были выделены Bounded Contexts.

### Пример разбивки на 2-недельные спринты

| Спринт | Задачи | Результат |
|--------|--------|-----------|
| S1 | Аудит зависимостей, Characterisation Tests, SonarQube baseline | «Подушка безопасности» |
| S2 | Обновление Java 8 → 11 (бэкенд), настройка CI/CD | Первый working build |
| S3 | Замена javax → jakarta (OpenRewrite), Hibernate 5 → 6 | Jakarta-ready |
| S4 | Spring Boot 2 → 3, Security 6 | Новый SecurityFilterChain |
| S5 | Java 11 → 17 → 21, Virtual Threads | Performance boost |
| S6 | Переход Angular 8 → 9 (Ivy) | Новый компилятор шаблонов |
| S7 | Переход Angular 9 → 12 (удаление View Engine) | Чистый Ivy |
| ... | ... | ... |

## 5.3. PI Planning и Roadmapping

Для миграции длиной 2+ года мы использовали **PI Planning (Program Increment)** из SAFe (Scaled Agile Framework).

### Структура Roadmap

```
Год 1: Фундамент
├── Q1 — Аудит, инфраструктура, CI/CD
├── Q2 — Java Backend migration (8 → 21)
└── Q3-Q4 — Angular migration (8 → 15)

Год 2: Трансформация
├── Q1 — Standalone Components + Signals
├── Q2 — Вырезание модулей (Strangler Fig)
└── Q3-Q4 — Microservices + Cloud deployment
```

### Как аргументировать сроки на собеседовании

> «Мы оценивали миграцию не в часах, а в **уменьшении технического долга по SonarQube**. Каждый PI мы ставили цель снизить Technical Debt Ratio на 3–5%. Это позволило бизнесу видеть прогресс, не вникая в технические детали.»

## 5.4. Risk Management: Откаты и Emergency Fix

Миграция живой системы с SLA 99.9% требует процедур отката (rollback plan).

### Стратегия отката для каждого релиза

1. **Feature Toggles** — каждый мигрированный модуль включался через тогл. Если что-то шло не так, тогл выключался без деплоя.
2. **Blue-Green Deployment** — старый и новый стек работали параллельно в разных средах.
3. **Canary Releases** — сначала 5% трафика, потом 25%, 50%, 100%.

### Emergency Fix процедура

```
Обнаружение критического бага на проде (P1)
  ├── 15 мин — GTI (Garantie de Temps d'Intervention)
  ├── Верификация — смотрим логи + New Relic / Grafana
  ├── Решение
  │   ├── Откат Feature Toggle (если возможно)
  │   └── Hotfix в текущей версии (без миграционных изменений)
  └── 2 часа — GTR (Garantie de Temps de Rétablissement)
```

## 5.5. Коммуникация с бизнесом: Демо каждого этапа

Бизнес-заказчик не понимает, зачем нужны Virtual Threads или Signals. Ему важно: **«Когда будет лучше? Не сломается ли текущее?»**

Мы выстроили коммуникацию через «слои бизнес-ценности»:

| Что мы сделали (технически) | Что видит бизнес |
|---------------------------|------------------|
| Java 8 → 21 (Virtual Threads) | Сервер выдерживает в 3 раза больше пользователей |
| Spring Boot 2 → 3 | Закрыли 45 CVE-уязвимостей — пройдем аудит безопасности |
| Angular 8 → 20 (Standalone + Signals) | Страницы грузятся в 2 раза быстрее, бандл уменьшился |
| Микросервисы + CI/CD | Релизы теперь каждую неделю вместо раза в месяц |
| SonarQube Quality Gates | 0 критических дефектов, соответствие ISO 27001 |

### Формат демо для бизнеса

Каждый месяц мы проводили **Steering Committee** (Комитет по управлению):

1. **Status** — что сделано (диаграмма Ганта, % complete).
2. **Metrics** — SonarQube, покрытие тестами, время сборки.
3. **Incidents** — сколько P1/P2 инцидентов, какое время восстановления.
4. **Next Steps** — что в следующем PI.

## 5.6. Reporting: Velocity, Burndown, Cycle Time

### Velocity и миграция

Скорость (velocity) в миграции измеряется не в story points, а в:

- **Module Migration Rate** — сколько модулей мигрировано / осталось.
- **Line of Code (LoC) migrated** — % кода на новой версии.
- **Technical Debt Ratio** — динамика по SonarQube.

### Burndown Chart

Наш burndown строился не по спринтам, а по **PI**:

```
PI-1: ████████████░░░░░░ 65% (Backend migration)
PI-2: ██████████████████░ 94% (Angular migration)
PI-3: ███████████████████ 100% (Microservices)
```

### Cycle Time

Мы отслеживали время от открытия тикета до деплоя на prod:

- До миграции: **14 дней** (ручное тестирование, долгий CI/CD).
- После миграции: **2 дня** (автоматизация, параллельные сборки).

## 5.7. Как рассказать про Agile на Senior-интервью

### Готовые формулировки

**Вопрос:** «Как вы организовывали процесс миграции?»

> «Мы работали в Scrum-ритме с 2-недельными спринтами, но с важной адаптацией: Product Owner'ом технической части выступал Tech Lead. Каждый спринт содержал не только миграционные задачи, но и бизнес-фичи (соотношение 70/30). Это позволило не копить technical debt по новой функциональности и сохранять прозрачность для бизнеса.»

**Вопрос:** «Как вы декомпозировали монолит?»

> «Мы использовали Event Storming для определения границ модулей (Bounded Contexts). Каждая User Story резала вертикальный слой — от базы данных до UI. Вырезанный модуль сразу покрывался Characterisation Tests через Testcontainers, затем переписывался на новый стек и вводился в эксплуатацию через Feature Toggle.»

**Вопрос:** «Что делать, если миграция идёт с опозданием?»

> «У нас был Stop-Go механизм раз в квартал: если Quality Gates не проходили или число инцидентов росло, мы останавливали миграцию и спринт посвящали стабилизации. Это позволяло не накапливать риск.»

### Шпаргалка терминов для собеседования (французский контекст)

| Французский термин | Русский эквивалент | Контекст |
|-------------------|-------------------|----------|
| **Analyse d'Impact** | Анализ влияния | Оценка, какие модули затронет изменение |
| **MCO (Maintien en Conditions Opérationnelles)** | Поддержка работоспособности | Режим TMA |
| **Garantie de non-régression** | Гарантия отсутствия регрессии | Покрытие тестами |
| **Recette** | Приёмочное тестирование | UAT (User Acceptance Testing) |
| **Bascule** | Переключение | Переход с одной версии на другую |
| **Lotissement** | Лотизация | Разбивка на фазы (phased approach) |

---

> **Подводный камень (Gotcha):** Никогда не говорите на собеседовании, что миграция шла «по Waterfall» или «без чёткого процесса». Даже если реальность была хаотичной, на интервью вы должны демонстрировать **осознанный процесс**: риски, метрики, адаптацию Scrum. Французские интервьюеры (особенно в ESN) высоко ценят процессное мышление.
