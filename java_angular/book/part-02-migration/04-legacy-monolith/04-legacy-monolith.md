# Глава 4: Legacy-монолит — Состояние «до» миграции

> «Чтобы понять, куда мы идём, нужно помнить, откуда мы пришли».

Любая миграция начинается с инвентаризации. Прежде чем переходить на Java 21 и Angular 20, необходимо зафиксировать «точку отсчёта» — то состояние технического долга, которое накопилось за годы production-эксплуатации. В этой главе мы детально разберём legacy-стек (Java 8, Angular 8, монолитную архитектуру) и проведём аудит проблем, которые предстоит решить.

---

## 4.1. Java 8: Ограничения и технический долг

Java 8 (выпущена в марте 2014 года) была революционной версией — именно она привнесла лямбды и Streams API. Однако за 10+ лет развития языка она превратилась в тормоз для современных практик разработки.

### 4.1.1. Старое Date/Time API

До Java 8 работа с датами и временем велась через `java.util.Date` и `java.util.Calendar`. Основные проблемы:

- **Мутабельность.** Объекты `Date` изменяемы. Передача ссылки на `Date` в другой метод могла незаметно изменить исходное значение (нарушение инкапсуляции).
- **Нетипобезопасность.** `Date` представлял и дату, и время без чёткого разделения. Не было разницы между `LocalDate`, `LocalTime`, `ZonedDateTime`.
- **Отсутствие Immutable-операций.** Метод `setYear()` менял сам объект, а не возвращал новый.

```java
// Старый стиль (Java 8-):
Date date = new Date(2020, 1, 1); // Deprecated!
date.setYear(2025); // Мутируем исходный объект — потенциальный баг

// Новый стиль (Java 8+):
LocalDate today = LocalDate.now();
LocalDate nextWeek = today.plusDays(7); // today остался неизменным
```

### 4.1.2. Отсутствие Records

В Java 8 не было `record` — неизменяемых классов-контейнеров для DTO. Приходилось вручную писать:

```java
public class UserDto {
    private Long id;
    private String email;

    public UserDto(Long id, String email) {
        this.id = id;
        this.email = email;
    }

    public Long getId() { return id; }
    public String getEmail() { return email; }

    @Override
    public boolean equals(Object o) { /* 15 строк бойлерплейта */ }
    @Override
    public int hashCode() { /* 10 строк */ }
    @Override
    public String toString() { /* 5 строк */ }
}
```

В Java 21 то же самое записывается одной строкой:

```java
public record UserDto(Long id, String email) {}
```

### 4.1.3. Verbose switch и отсутствие Pattern Matching

В Java 8 оператор `switch` работал только с числами, строками и enum-ами. Не было возможности использовать `switch` как выражение, а Pattern Matching для `instanceof` появился лишь в Java 16+.

```java
// Java 8: громоздкий switch
String result;
switch (day) {
    case MONDAY:
    case FRIDAY:
        result = "Work";
        break;
    case SATURDAY:
    case SUNDAY:
        result = "Rest";
        break;
    default:
        result = "Unknown";
}

// Java 21: switch expression с Pattern Matching
String result = switch (day) {
    case MONDAY, FRIDAY -> "Work";
    case SATURDAY, SUNDAY -> "Rest";
    default -> "Unknown";
};
```

### 4.1.4. Старый Garbage Collector (CMS)

Java 8 активно использовала сборщик **CMS (Concurrent Mark Sweep)**, который:

- Фрагментировал память (не уплотнял кучу после сборки).
- Требовал тонких настроек JVM (`-XX:+UseConcMarkSweepGC`, `-XX:CMSInitiatingOccupancyFraction`).
- Был **удалён в Java 14**, что стало проблемой при миграции: старые JVM-флаги в Docker-контейнерах вызывали ошибки запуска.

```bash
# Типичный скрипт запуска Java 8 приложения:
java -XX:+UseConcMarkSweepGC -Xms2g -Xmx4g -jar app.jar

# На Java 21 эта команда упадёт с ошибкой:
# "Unrecognized VM option 'UseConcMarkSweepGC'"
```

### 4.1.5. Отсутствие модульной системы (Jigsaw)

Java 8 не имела модульной системы (Project Jigsaw появился в Java 9). Это означало:

- Вся JDK была монолитной (rt.jar, tools.jar).
- Не было строгой инкапсуляции внутренних API (`sun.misc.*`).
- Рефлексия могла получить доступ к любым классам JVM.

При переходе на Java 9+ старые библиотеки (Lombok, Jackson) ломались из-за `InaccessibleObjectException`.

## 4.2. Angular 8: Ограничения и технический долг

Angular 8 (выпущен в мае 2019 года) работал на **View Engine** — старом компиляторе шаблонов. Переход на Angular 9+ потребовал полной перестройки внутреннего механизма рендеринга.

### 4.2.1. NgModule boilerplate

Каждый компонент, директива или пайп требовал обязательной регистрации в файле `*.module.ts`:

```typescript
// Angular 8: обязательный NgModule
@NgModule({
  declarations: [UserProfileComponent],  // Регистрируем
  imports: [CommonModule, FormsModule],  // Импортируем целые модули
  exports: [UserProfileComponent]
})
export class UserModule { }
```

Проблемы:
- **«Двойной импорт»** — сначала ES-import вверху файла, потом регистрация в `declarations`.
- **SharedModule анти-паттерн** — разработчики сваливали всё в один гигантский модуль, убивая Tree-Shaking.
- **Lazy Loading требовал создания отдельного NgModule** — даже для одного ленивого компонента.

### 4.2.2. Старый RxJS (v6)

Angular 8 использовал RxJS 6, который:

- Требовал оператор `pipe()` для всех цепочек (в RxJS 5 был «чистый» chain).
- Не имел `firstValueFrom()` / `lastValueFrom()` — для преобразования Observable в Promise использовался `.toPromise()`, который **удалён в RxJS 7**.
- Позволял устаревший синтаксис подписок: `.subscribe(successFn, errorFn)` вместо современного объектного коллбека.

```typescript
// Angular 8 / RxJS 6 — устаревший стиль
this.http.get('/api/users').subscribe(
  users => this.users = users,
  err => console.error(err)
);

// Современный Angular / RxJS 7+ — объект-наблюдатель
this.http.get('/api/users').subscribe({
  next: users => this.users.set(users),
  error: err => console.error(err)
});
```

### 4.2.3. Отсутствие Standalone-компонентов

Все компоненты были **зависимы от NgModule**. Нельзя было просто импортировать компонент через ES-import и использовать его — требовалась регистрация в модуле. Это усложняло:

- Переиспользование компонентов между проектами.
- Unit-тестирование (нужен был `TestBed.configureTestingModule` с фиктивным NgModule).
- Tree-Shaking (сборщик не мог вырезать неиспользуемые компоненты из бандла).

### 4.2.4. Старая система Change Detection (Zone.js)

Angular 8 полностью полагался на библиотеку `zone.js`, которая «патчила» все асинхронные операции браузера:

- При любом событии (клик, таймер, fetch) Zone.js запускала **полный проход Change Detection по всему дереву компонентов**.
- На сложных страницах это приводило к падению FPS, дёрганью интерфейса.
- Не было точечной реактивности (Signals) — каждое изменение стейта вызывало перепроверку сотен компонентов.

### 4.2.5. Размер бандла и сборка

- Angular 8 использол **Webpack 4** (без поддержки ESBuild и инкрементальной компиляции).
- Финальный JS-бандл мог весить **10–15 МБ** из-за плохого Tree-Shaking в View Engine.
- Время сборки (cold build) достигало 5–10 минут на CI/CD.

## 4.3. Монолитная архитектура: Проблемы

Проект до миграции представлял собой **монолитное приложение** (один WAR/EAR-артефакт, развёрнутый на Java EE сервере, например WildFly/JBoss).

### 4.3.1. Связывание развёртывания (Deployment Coupling)

- Любое изменение в любом модуле (биллинг, нотификации, профиль) требовало **перезапуска всего монолита**.
- Нельзя было обновить один сервис без остановки других.
- Релизный цикл занимал 2–4 недели из-за необходимости полного регрессионного тестирования.

### 4.3.2. Ограничения масштабирования

- Монолит масштабировался только как единое целое (горизонтально — копированием всей JVM).
- Разные модули имели разные профили нагрузки: модуль отчётов потреблял много CPU, а модуль уведомлений — много памяти. Приходилось выбирать компромисс.

### 4.3.3. Сложность тестирования

- Интеграционные тесты требовали поднятия всего контекста Spring (десятки бинов, соединения с БД).
- Невозможно было тестировать изолированный модуль без старта всего приложения.
- Время прогона тестов на CI/CD достигало 1–2 часов.

### 4.3.4. Отсутствие изоляции сбоев

- Ошибка в модуле отчётов (например, `OutOfMemoryError`) валила всё приложение, включая платёжный модуль.
- Не было Circuit Breaker'ов — если один модуль зависал, зависали и все остальные.

## 4.4. Инвентаризация технического долга

Перед началом миграции мы провели аудит кодовой базы (Analyse d'Impact).

### 4.4.1. EOL-библиотеки (End of Life)

| Библиотека | Версия | Статус | Действие |
|-----------|--------|--------|----------|
| Angular CDK | 8.x | End of Life | Обновить до 18+ |
| RxJS | 6.x | End of Life | Обновить до 7.8+ |
| Spring Boot | 2.1.x | End of Life | Обновить до 3.x |
| Hibernate | 5.3.x | End of Life | Обновить до 6.x |
| JUnit | 4.x | End of Life | Обновить до 5.x |

### 4.4.2. SonarQube Quality Gates

Типичные показатели legacy-проекта:

- **Code Coverage:** ~35% (требование: 80%)
- **Code Smells:** 1500+ (включая дублирование кода, закомментированный код, глубокое ветвление)
- **Security Hotspots:** 45 (SQL-инъекции, hardcoded credentials, устаревшие криптоалгоритмы)
- **Technical Debt Ratio:** 28% (проект требовал ~6 человеко-месяцев на исправление)

### 4.4.3. Dependency conflicts

В legacy-проектах часто возникает «ад зависимостей» (JAR hell):

```xml
<!-- Конфликтующие транзитивные зависимости -->
<dependency>
    <groupId>com.google.guava</groupId>
    <artifactId>guava</artifactId>
    <version>19.0</version>
</dependency>
<dependency>
    <!-- Транзитивно тянет Guava 23.0 через другую либу -->
    <groupId>org.apache.hbase</groupId>
    <artifactId>hbase-client</artifactId>
    <version>2.0</version>
</dependency>
```

При сборке Maven/Gradle мог взять неправильную версию, вызывая `NoSuchMethodError` в рантайме.

## 4.5. Итоги: «Карта боли» (Pain Map)

Составим сводную карту проблем, которые предстоит решить в миграции:

| Область | Ключевые проблемы | Влияние на бизнес |
|---------|------------------|-------------------|
| **Java 8** | Нет Virtual Threads, Records, Pattern Matching | Ограниченная масштабируемость, много бойлерплейта |
| **Angular 8** | NgModule, View Engine, Zone.js | Большие бандлы, медленная сборка, утечки памяти |
| **Монолит** | Deployment coupling, масштабирование | Долгие релизы, риск простоев |
| **Библиотеки** | EOL-версии, CVE-уязвимости | Нарушение комплаенса, риски безопасности |
| **Тестирование** | Низкое покрытие, медленные тесты | Страх изменений, баги на проде |
| **Архитектура** | Нет изоляции, нет Graceful Degradation | Каскадные сбои |

---

> **Подводный камень (Gotcha):** Не пытайтесь исправить всё сразу в рамках миграции. Legacy-проекты накапливали технический долг годами. Ваша задача — не сделать код идеальным, а **убрать критические блокеры для дальнейшего развития**. Для каждого пункта из «карты боли» нужно принять решение: фиксим сейчас или откладываем в бэклог.
